## Шаги — проход `titles`
1. Прочитать входы бегло: факты, трения, пробелы, относящиеся к {CATEGORIES}.
2. Набрать заголовки: затравки библиотеки, прошедшие сигнал применимости, + **свои** идеи (не меньше 30 %). Пропускать всё, что уже есть в продукте, и всё, что по смыслу пересекается с {OTHER_TITLES} (то же другими словами — тоже пересечение).
3. Для каждого: `id` (`{GROUP}-NN`), `title` (≤ 90 знаков), `category`, `description` — **одна строка ≤ 160 знаков**: что и для кого, `source_group`. Больше полей не заполнять.
4. Веб-поиск — не больше 2 запросов (только проверить, что идея — не уже существующая функция продукта или платформы).

## Шаги — проход `details`
1. Прочитать входы. Выписать для себя 10–15 главных фактов, трений и пробелов, относящихся к твоим категориям.
2. Развернуть {MY_TITLES}; можно добавить до 10 % новых, не пересекающихся с {OTHER_TITLES}. Снятые с группы заголовки не возвращать.
3. **Перед словом «нет»** в `current_feature` и `description` — проверить по `repo-scan.json` и `product-understanding.md`, что функции действительно нет, и в каком тарифе/режиме она есть (бесплатно, платно, только в демо).
4. Для каждой идеи найти доказательство: живая функция конкурента, документация платформы, обсуждение сообщества, Issue, наш код/скриншот. Сначала — `sources.json`; новые URL — только открытые тобой (код 200).
5. Определить **предпосылки** (`dependencies`): что должно существовать раньше, чтобы предложение сработало.
6. Отбросить: дубли существующих функций, запрещённое, без доказательства и без логики (даже D требует цепочки рассуждения).
7. Заполнить объекты по схеме, проставить черновые `scores` строго по якорям.
8. Перечитать всё целиком: нет ли дублей внутри группы и с {OTHER_TITLES}, конкретны ли шаги, правдивы ли доказательства, заполнены ли предпосылки.

## Требования к полям (проход `details`)
- `id`: `{GROUP}-01`, `{GROUP}-02`, … (как в проходе `titles`); `source_group`: `{GROUP}`; `merged_from` не заполнять; `mockup`: `null`.
- `category` — одна из {CATEGORIES} (коды контракта); число по категориям — по {QUOTAS} (±10 %).
- `title` ≤ 90 знаков, начинается с глагола или существительного-результата; `description` — что именно сделать, где и для кого; `rationale` — почему сработает (механизм + факт).
- `evidence[]`: `kind`, `url` **или** `file` (`путь:строка`), `title`, `note` (пересказ или цитата < 15 слов, одна цитата на источник), `checked`: {DATE}.
- `evidence_class`: A — первоисточник или живая функция; B — ≥ 2 независимых источника (две записи `evidence`); C — одно упоминание; D — логический вывод (`url: null` и `file: null` допустимы, цепочка рассуждения в `note` обязательна). Issues одного автора или собственного QA — не выше C. Наш код (`kind: repo`) доказывает, что функция есть или её нет в продукте, но **не** доказывает рыночный спрос: для рыночного тезиса нужен внешний источник. Цель группы — A+B ≥ 60 % (внутренние и внешние доказательства считаются отдельно, `references/methodology-anchors.md`).
- `current_feature`: что есть сейчас (`путь:строка` или скриншот `mockups/current/…png`) либо «нет» с пояснением, где проверено.
- `dependencies`: **обязательны**, если у предложения есть предпосылки — демо без регистрации и его хостинг, открытый репозиторий, лицензия, установщик, платёжный путь и статус продавца, API или интеграция, аналитика для измерения, перевод, юридические документы. Значение — id предложений своей группы (`{GROUP}-NN`) или из {OTHER_TITLES}; если предпосылки нет ни в одной группе — назови её в отчёте (пункт 3), её превратит в предложение оркестратор или аудитор фазы 5.5. Только то, без чего предложение не работает, — не «похожие» предложения. Нет предпосылок — `[]`.
- `effect_kpi[]`: KPI, направление, диапазон, `label`: `факт`/`оценка`/`допущение`.
- `steps[]`: 3–7 шагов «что — где — как», `doc_url` — реальная документация из источников или `null`.
- `effort_days` [min, max] для одного разработчика; `cost_money` в {CURRENCY}; `risks` — каждая шкала 1–5 + `note`.
- `time_to_first_result_days`, `cheap_test` — проверка за дни, а не недели (фейковая дверь, опрос, прототип, ручная версия).
- `scores`: `value`, `cost`, `risk`, `confidence` — обязательно; подшкалы — по таблице «Какие подшкалы заполнять» в якорях. `confidence` не выше потолка класса.
- `kano`: `must|linear|delight|indifferent`; `horizon`: `now|next|later|vision`; `horizon_years`: 0/0/1/2+. Горизонт не раньше горизонта предпосылок.
- Хотя бы 2–3 предложения группы — горизонта `later`/`vision` (многолетние ставки), если категория это допускает.

## Формат отчёта (до 30 строк)
Проход `titles`: файл, число заголовков по категориям, 3–5 заголовков, которые могут пересекаться с другими группами (если сомневаешься).
Проход `details`:
1. Файл, число предложений по категориям, распределение классов A/B/C/D.
2. 5 сильнейших предложений (id, название, почему).
3. Предпосылки: сколько предложений с `dependencies`; предпосылки, которых нет в реестре («нужно: …» → для каких id).
4. Что отброшено и почему (кратко, числом и примерами).
5. Новые URL, которых не было в `sources.json` (список).
6. Расхождения с фактами входов: факт — как во входах — как нашёл ты — источник (`путь:строка` или URL), или «нет».
7. Допущения `[ДОПУЩЕНИЕ]`.
8. Обращения к ИИ в данных или «нет».
9. Использовано поисков / открытий страниц.

## Режим идеи (mode: concept)
Действует, когда `{MODE}` = `concept`: продукта ещё нет, есть досье идеи (`{OUT}/research/idea-dossier.md`, `{OUT}/data/idea.json`), репозиторий не сканировался. Правила выше остаются, кроме перечисленного:
- Вместо кода и скриншотов продукта читай досье идеи, `{OUT}/research/concept-canvas.md` (если уже есть), `competitors.json` (в т. ч. `kind`, `lessons`, `why_it_worked_or_failed`) и `market.md`. Файлов `repo-scan.json`, `repo-facts.json`, `ui-inventory.md`, `issues*.json`, `mockups/current/` нет — не искать (они в {MISSING_INPUTS}).
- `current_feature` — всегда «нет (продукта ещё нет)». «Уже есть» ({EXISTING}) — пусто или то, что у владельца есть вне продукта (аудитория, домен, прототип) — из досье.
- Предложения — **решения для MVP, запуска и проверок**: состав и границы функций MVP, онбординг и пустые состояния, модель и цены, каналы предзапуска и запуска, дешёвые проверки гипотез (фейковая дверь, интервью, лендинг, прототип), юридические и платформенные предпосылки (юрлицо, домен, аккаунты магазинов). Не предлагать «улучшить», «ускорить», «исправить» несуществующее.
- Обязательный тег в `tags` — ровно один из `mvp` | `v1` | `later` (граница: `mvp` — без этого первый запуск не имеет смысла; `v1` — после подтверждения гипотез; `later` — долгие ставки); `horizon` согласовать с тегом (`mvp` → `now`, `v1` → `next`, `later` → `later|vision`).
- Доказательства (`evidence`) — аналоги и конкуренты из `competitors.json`, сообщества, документация платформ и сервисов, исследования рынка; `kind: repo` и `own_app` не использовать. Класс A/B — только по внешним источникам; обсуждение владельца в досье — не выше C. Нет внешнего источника — класс D с цепочкой рассуждения.
- Цифры (`effect_kpi`, `time_to_first_result_days`, цены) — с меткой `допущение`, пока нет внешнего источника; `cheap_test` обязателен и должен выполняться **до** разработки.
- `dependencies` — только настоящие предпосылки запуска (аккаунт магазина, домен, лист ожидания для проверки, платёжный путь); предложения `later` не могут быть предпосылкой для `mvp`.
