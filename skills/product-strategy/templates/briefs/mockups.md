## Шаги
1. Посмотреть эталон и скриншоты; понять компоненты набора. **Набор не писать заново** и не копировать к себе: всё нужное уже в `_kit.css` — в том числе (1.3) график с легендой и уровнями `.ps-chart`/`.ps-legend`/`.ps-level`, `kbd.ps-kbd`, ползунок `.ps-slider`, свежесть данных `.ps-fresh`, степпер `.ps-stepper`, счётчик `.ps-counter`, «пузырь» чата `.ps-msg`, сноски `.ps-fn`, сравнение `.ps-yes/.ps-no/.ps-unk`, шапка/подвал сайта, нижняя панель действий `.ps-actionbar`/`.pm-actionbar`; не хватает компонента — собрать его в своём макете с префиксом ключа и сообщить в отчёте.
2. Для каждого ключа: продумать сценарий (что видит пользователь, главное действие, состояния), затем собрать `mockups/concepts/<key>.html` на наборе.
3. Подключение в `<head>`: `<link rel="stylesheet" href="../tokens.css"><link rel="stylesheet" href="_kit.css"><link rel="stylesheet" href="_icons.css">` (+ `<link rel="stylesheet" href="_mobile.css">` для мобильных, + `<script src="_kit.js" defer></script>`, если есть). Размер и связи — атрибутами `<html>` или `<meta name="ps:…">`: `data-viewport` / `ps:viewport` (`390x844` — один экран телефона, `1720x1000` — раскадровка из 4 экранов, `1320x1000` — из 3, `900x1000` — из 2, `1440x900` — десктоп), `data-proposals` / `ps:proposals` (P-id через запятую). По ним скрипт снимков сам находит макет и размер и обновляет индекс при правке — индекс макетов не нужен. Мобильный экран — копия `_base-mobile.html`, раскадровка — копия `_storyboard.html` (номер кадра — `data-screen` у `.pm-frame`).
4. Тема: по умолчанию светлая; если набор поддерживает тёмную (`data-theme="dark"`) и экран важен в обеих — можно второй вариант в том же файле или отдельным ключом `<key>-dark` (согласовано в {KEYS}).
5. Бейдж — одно правило набора (README, «Бейдж концепта»): текст `Концепт, не существующая функция · {PRODUCT} · {DATE}` в элементе с классом `ps-concept-badge`, виден и не закрывает главное. Телефон — полосой `ps-concept-badge is-strip` первым элементом `.pm-phone` (на каждом экране раскадровки; не влезает — убрать дату, затем название: текст не должен обрезаться); длинная страница или раскадровка — `is-inline` (в потоке; `position: fixed` на полном снимке уезжает вниз); десктоп с нижней панелью — `is-above-nav`. Проверка — по классу; обрезанный текст бейджа — замечание `shoot_mockups`.
5а. Подсветка элементов (стандарт макета): разметь **12–25 элементов** экрана — `data-hs="<id>" data-hs-title="…" data-hs-what="что это" data-hs-why="для чего" data-hs-p="P0xx" data-hs-sec="<раздел стратегии>"` у существующих элементов (вид не меняется) и подключи последней строкой `<body>` `<script src="_hotspots.js"></script>`.
5б. Принцип взаимодействия (`references/design.md` §3.1; обязателен при `design.pointer_first`): всё доступно кнопками и касанием, клавиши — ускорение (`kbd.ps-kbd` рядом с кнопкой), цели ≥ 32 px (мышь) / ≥ 44 px (касание), перетаскивание дублируется кнопками (`data-drag-alt="<селектор кнопок>"`).
5в. Пробелы и расхождения с реестром — комментарием в макете строго в формате `<!-- НУЖНО-ПРЕДЛОЖЕНИЕ: <заголовок> | <категория> | <связанные P-id> -->` и `<!-- РАСХОЖДЕНИЕ: <P-id> | <суть> -->` (собирает `link_mockups.py --collect-gaps`); P-id не выдумывать.
5г. Канон демо-данных (если есть `data/demo-canon.json`): у каждого элемента с числом, датой или именем из канона — `data-canon="<ключ>"` (ключ из `values` канона, например `model.price_month`, или `<кейс>.<поле>` кейса ядра прототипа, например `C01.paybackWeeks`; текст элемента — значение канона, числа можно округлить для показа); повторяющиеся элементы графика (значки, точки, строки) — `data-canon-item="<ключ>"`, их число равно значению канона. Новых демо-сущностей в макете не вводить — строкой отчёта «добавить в `entities` канона: …». Проверка: `python3 {SKILL_DIR}/templates/prototype-kit/tools/check_canon.py {OUT} --html {OUT}/mockups/concepts/<ключ>.html` → «расхождений нет» (нет канона — код 2, пропустить).
6. Рендер и проверка только своих ключей: `PS_NODE_DIR=<кэш Node-модулей из факт-листа или ~/.cache/product-strategy/node> node {SKILL_DIR}/scripts/node/shoot_mockups.mjs {OUT} --only <ключ>[,<ключ>…] --contrast --other-theme --layout --targets --hotspots 12` (вторая тема — `<ключ>.theme-<тема>.png`; `--targets` — цели нажатия, `--layout` — обрезанные кнопки в рядах; черновые id `G8-xx` в `data-proposals` допустимы) → PNG рядом с HTML и `{OUT}/data/mockups-check.<ключ>.json` (свой файл на ключ; с `--only` общие `mockups-index.json` и `mockups-check.json` не пишутся — параллельные агенты не мешают друг другу). Открыть свой PNG через Read, исправить дефекты, повторить. Замечание «использован запасной цвет набора» — токены продукта не дошли до набора: не подгонять цвета в макете, а сообщить в отчёте. «Страница выше viewport» у раскадровки — поднять высоту `data-viewport` (≥ 960–1000); длинная страница по замыслу — `--full-page`. Флаги — `--help`.

## Правила
- Язык интерфейса — {LANG} (как в продукте). Тексты правдоподобные, без lorem ipsum, без персональных данных реальных людей.
- Детально, на компонентах набора; новых классов — с префиксом ключа (`m05-…`), чтобы не конфликтовать. Иконки — `ps-i ps-i-<имя>` из `_icons.css` (список — в его шапке), не эмодзи и не внешние шрифты иконок.
- Новое и изменённое на экране — метками `ps-new` («НОВОЕ») и `ps-changed` («ИЗМЕНЕНО»); в контейнере с `overflow: hidden` — с `is-inside`, свой `::before` с меткой не делать.
- Без внешних запросов (шрифты, CDN, картинки по сети); только локальные файлы.
- Не копировать чужие логотипы, иллюстрации, тексты; паттерны конкурентов — своими компонентами.
- Контраст текста ≥ 4,5:1 (крупный ≥ 3:1), в том числе для бейджей, кнопок-предупреждений и текста на штриховке; кликабельные зоны ≥ 24 px.
- `_kit.css`/`_icons.css`/`_mobile.css`/`_kit.js`/`_hotspots.js`/`tokens*.css`/`_base*.html`/`_storyboard.html`/`M00-design-language.html` не менять (`mockup_kit.py verify` сверяет с `build/kit.lock`); нашёл баг набора — описать в отчёте (оркестратор исправит один раз для всех).
- Временные файлы — только в `{OUT}/build/tmp/<имя файла этого брифа без .md>/` (например, `build/tmp/mockups-M05/`).
- Не запускать git; писать только в пути из «Выдачи».

## Формат отчёта (до 20 строк)
По строке на макет: ключ, что показывает, P-id, viewport, тема, размечено элементов `data-hs` и `data-canon`, проблемы; число строк `НУЖНО-ПРЕДЛОЖЕНИЕ`/`РАСХОЖДЕНИЕ` в макетах; значения, которых не хватило в каноне демо-данных; найденные баги набора (класс, симптом, предложение); компоненты, которых не хватило; экран не работает без предложения, связи с которым нет в `dependencies`, — строкой `ПРЕДПОСЫЛКА: P038 ← P033 | почему`; расхождения с фактами входов (факт — как во входах — как увидел — источник) или «нет»; допущения о продукте; что осталось спорным.
