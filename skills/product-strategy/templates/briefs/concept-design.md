# Бриф: язык дизайна и концепт-макеты нового продукта — {PRODUCT} (режим идеи)

Плейсхолдеры: `{OUT}` (папка прогона от корня репозитория), `{SKILL_DIR}` (через `~`), `{PRODUCT}` (рабочее название идеи; финальное название ещё не выбрано — не оформлять его как утверждённое), `{LANG}`, `{DEPTH}`, `{DATE}`, `{MODE}` (`concept`), `{IDEA_FACTS}` (5–12 строк: идея, аудитория, ядро ценности, MVP, платформа и тип продукта), `{DESIGN_ANSWERS}` (ответы владельца по теме «дизайн и бренд»: настроение, референсы, цвета, «как не должно выглядеть», бренд-ограничения, или «не заданы — допущения»), `{PRODUCT_TYPE}` (`saas|consumer|devtool|oss|content|game|bot|mobile|desktop|other`), `{STEPS}` (`1` — только направления, для выбора владельцем; `2-3` — токены и макеты по выбранному направлению; `1-3` — всё сразу), `{CHOSEN}` (направление, выбранное владельцем, или «нет» — взять рекомендованное), `{MOCKUPS_MIN}` (минимум макетов, по умолчанию 8), `{KEYS}` (ключи макетов этого агента с темами и P-id или «все»), `{VIEWPORTS}` (какие ключи мобильные), `{MISSING_INPUTS}`.

Модель: opus (дизайнерское суждение, синтез по аналогам и ответам владельца).

## Цель
Продукта ещё нет, а владельцу нужно **увидеть** его до разработки. Выполнить три шага: (1) предложить **три направления языка дизайна** и порекомендовать одно; (2) записать токены выбранного направления в `mockups/tokens.css` (обе темы); (3) нарисовать не меньше {MOCKUPS_MIN} **концепт-макетов** ключевых экранов на готовом наборе компонентов. Макеты — **гипотезы** о том, как продукт мог бы выглядеть и работать; они не доказывают, что людям это понятно и нужно, и обязаны быть проверены на людях (см. «Проверка на людях» ниже).

## Шаг 1. Три направления языка дизайна (если {STEPS} содержит 1)
Записать `{OUT}/design/directions.md`. Для **каждого** из трёх заметно различающихся направлений (не три оттенка одного):
- **Название** и одна фраза-суть; **настроение** (3–5 слов) и кому оно подходит из персон.
- **Палитра светлой и тёмной темы в hex:** фон `bg`, поверхность `surface`, текст `text`, приглушённый текст `muted`, акцент `accent` и текст на акценте `on-accent`, рамка `border`, успех/предупреждение/опасность (+ `on-danger`). **Проверить контраст** (способ ниже): `text` на `bg` и `surface` ≥ 4,5:1; `muted` на `bg` и `surface` ≥ 4,5:1; `on-accent` на `accent` ≥ 4,5:1; `on-danger` на `danger` ≥ 4,5:1; `accent` на `bg` ≥ 3:1. Таблица «пара → отношение» по обеим темам обязательна; значения посчитаны, а не прикинуты.
- **Типографика — только из безопасных шрифтов системного стека** (никаких веб-шрифтов и CDN): например `system-ui, -apple-system, "Segoe UI", Roboto, "Helvetica Neue", Arial, sans-serif`; характер задают стеком, а не файлами: гуманистический/геометрический без засечек, `ui-serif, Charter, Georgia, "Times New Roman", serif` для заголовков, `ui-monospace, SFMono-Regular, Menlo, Consolas, monospace` для технических акцентов. Указать семейства для заголовков и текста, базовый размер, шкалу (5–6 размеров), начертания. Не утверждать, что нестандартный шрифт установлен у всех.
- **Формы:** радиусы (`--radius`, `--radius-lg`), плотность и отступы, тени/границы, характер кнопок и карточек. **Иконки:** стиль (линейные/залитые, толщина, скругления) и источник — свои простые SVG/символы без внешних загрузок; чужие наборы не копировать.
- **Тон текстов:** 3 правила + пример кнопки, пустого состояния и сообщения об ошибке в этом тоне.
- **На чём основано:** (а) ответы владельца по дизайну (цитата или ключ из `idea.json`), (б) сильные решения аналогов из `competitors.json` — `slug` + что именно (паттерн, не внешний вид) + URL из `sources-competitors.json`, (в) персоны/позиционирование из `concept-canvas.md`. Что **не** берём и почему (в т. ч. тёмные паттерны).
- **Риски направления:** что может не сработать (доверие, доступность, перегрузка), как это проверить.

Затем раздел **«Рекомендация»**: какое направление выбрано и почему (3–5 пунктов с отсылкой к ответам владельца и аналогам), что стоит показать пользователям при проверке, как направление поведёт себя на мобильном. Если задан {CHOSEN}, рекомендуется выбранное владельцем (расхождение с мнением агента — отдельной строкой «моё замечание», без подмены выбора). Если {STEPS} = `1` — после `directions.md` остановиться (владелец выберет; шаги 2–3 выполнит следующий запуск).

Проверка контраста — один и тот же скрипт для пары цветов и для файла токенов (сохранять не нужно; запуск из stdin):
```
python3 -I - '#111316' '#e7e9ec' <<'PY'
import re,sys
def lum(h):
    h=h.lstrip('#'); h=h*2 if len(h)==3 else h
    c=[int(h[i:i+2],16)/255 for i in (0,2,4)]
    c=[x/12.92 if x<=.03928 else ((x+.055)/1.055)**2.4 for x in c]
    return .2126*c[0]+.7152*c[1]+.0722*c[2]
def cr(a,b):
    x,y=sorted((lum(a),lum(b)),reverse=True); return (x+.05)/(y+.05)
if len(sys.argv)==3 and sys.argv[1].startswith('#'):
    print(round(cr(sys.argv[1],sys.argv[2]),2)); sys.exit()
T={}
for sel,body in re.findall(r'([^{}]+)\{([^}]*)\}',open(sys.argv[1]).read()):
    th='dark' if 'dark' in sel and 'light' not in sel else 'light'
    T.setdefault(th,{}).update(dict(re.findall(r'--([\w-]+)\s*:\s*(#[0-9a-fA-F]{3,6})\b',body)))
P=[('c-text','c-bg',4.5),('c-text','c-surface',4.5),('c-muted','c-bg',4.5),('c-muted','c-surface',4.5),('c-on-accent','c-accent',4.5),('c-on-danger','c-danger',4.5),('c-accent','c-bg',3)]
bad=[(th,a,b,round(cr(v[a],v[b]),2)) for th,v in T.items() for a,b,m in P if a in v and b in v and cr(v[a],v[b])<m]
print(sorted(T),'FAIL' if bad else 'ok',bad)
PY
```
Две hex-строки в аргументах → отношение контраста; вместо них путь к CSS (`python3 -I - {OUT}/mockups/tokens.css <<'PY' …`) → проверка файла токенов по обеим темам, ожидается `['dark', 'light'] ok []`.

## Шаг 2. `mockups/tokens.css` (если {STEPS} содержит 2)
Записать `{OUT}/mockups/tokens.css` для рекомендованного (или выбранного) направления — **в формате, который пишет `audit_site.mjs`** (`references/design.md` §1, `data-contract.md` «Уточнения по итогам 1.1», набор — `templates/mockup-kit/README.md`):
- **тёмный блок первым**: селектор `:root[data-theme="dark"], [data-theme="dark"]:not(:root)`; **светлый — последним**: `:root, [data-theme="light"]` (сборщики берут последнее значение переменной, поэтому светлые значения — по умолчанию);
- переменные в обоих блоках одинаковые: `--c-bg`, `--c-surface`, `--c-text`, `--c-muted`, `--c-accent`, `--c-on-accent`, `--c-border`, `--c-success`, `--c-warning`, `--c-danger`, `--c-on-danger`, `--c-focus`, `--shadow`; общие (можно в светлом блоке) — `--radius`, `--radius-lg`, `--font`, `--font-heading`, `--font-size`;
- цвета — **только hex** (`#rrggbb`): график и сборщики читают hex; `--font`/`--font-heading` — системный стек без `url(...)`;
- у каждой переменной есть пара в тёмной теме; 3–5 нейтральных, не 20; комментарий в начале файла: направление, дата, «концепт, финальный бренд не утверждён».
Проверка: скрипт выше по файлу → `['dark', 'light'] ok []`; если нужные цвета не проходят — скорректировать палитру направления (и записать это в `directions.md`), а не ослаблять порог.

Набор экранов — не меньше {MOCKUPS_MIN} (по `{KEYS}`), под тип {PRODUCT_TYPE}; по умолчанию:

2. **Онбординг / первый запуск** (путь до первой ценности за минимальное число шагов).

## Формат отчёта (до 25 строк)
1. Файлы; рекомендованное направление и почему (одна строка); три направления одной строкой каждое.
2. Таблица макетов: ключ, что показывает, P-id, viewport, тема, проблемы. Экраны без подходящего предложения («нужно предложение: …»).
3. Контраст: пары, которые пришлось подправить, и итог проверки токенов.
4. Найденные баги набора (класс, симптом, предложение); компоненты, которых не хватило.
5. Что в макетах — допущение и что проверить на людях в первую очередь.
6. Расхождения с фактами входов (факт — как во входах — как увидел — источник) или «нет»; допущения `[ДОПУЩЕНИЕ]`; обращения к ИИ в данных или «нет».
