# Оркестрация: что делать самому, что раздавать

Оркестратор — сессия, в которой запущен скилл. Субагенты (Agent tool) получают только бриф — они не видят разговор, `SKILL.md` и этот файл, если бриф не велит их прочитать.

## Разделение работы

| Делает оркестратор сам | Раздаёт субагентам |
|---|---|
| опрос, конфиг, git, `TASKS.md`/`STATUS.md` | сбор данных фазы 4 (конкуренты, сообщества, запросы, события, право) |
| запуск приложения и `audit_site.mjs` (один браузер, порядок важен) | генерация кандидатов реестра по группам категорий |
| понимание продукта (фазы 1, 3) — короткий синтез, нужен целиком в голове | карточки конкурентов по скриншотам |
| слияние реестра, калибровка оценок, запуск `score.py` и проверок | разделы стратегии (кроме резюме), спеки, эксперименты, гант и канбан |
| факт-лист для авторов стратегии, резюме, склейка `strategy.md` | макеты (после того как оркестратор сделал дизайн-язык) |
| дизайн-язык: `_kit.css` + демо-экран | карточки design-refs, узлы блок-схем |
| сборка форматов, QA-ворота, отчёт | точечные правки по списку дефектов |
| разбор расхождений между агентами | второй независимый оценщик топ-30 (deep/exhaustive) |

Правило: если результат нужен оркестратору целиком для следующих решений (понимание продукта, ставки, калибровка) — делать самому. Если работа параллелится по непересекающимся файлам и проверяется скриптом — раздавать.

## Выбор модели

1. Если установлен скилл `typesafe-triage` (в списке скиллов или `check_env.py` нашёл его): собрать подзадачи фазы в `build/triage-<фаза>.json` — список `{"id", "task", "paths": [...]}` (`task` — одна-две фразы сути брифа без данных продукта и без кода) — и вызвать `python3 <путь typesafe-triage>/scripts/typesafe_triage.py --batch build/triage-<фаза>.json`. Взять из вывода `model`/`effort` и порядок (пересекающиеся `paths` — последовательно). Если вывод требует подтверждения пользователя (haiku, fable, effort low/max) — один вопрос на весь пакет; без ответа — sonnet/opus и medium/xhigh.
2. Нет скилла или ключа — правило по умолчанию:

| Работа | Модель |
|---|---|
| сбор данных, поиск, выписки, скриншоты, карточки конкурентов, классификация Issues, гант/канбан из готового плана, механические правки | sonnet |
| синтез, оценка и калибровка, разделы стратегии, спеки, эксперименты, правовой обзор, дизайн-язык, макеты, design-refs, рисование схем | opus |
| генераторы реестра | sonnet; opus — для групп `product`, `monetization`, `platform` на deep/exhaustive |

3. **Всегда указывать `model` у Agent явно** — иначе агент наследует модель сессии. Параметр `effort` ставить, только если этого явно требует пользователь, его CLAUDE.md или заметка триажа; иначе глубину задавать словами в брифе («проверь каждую ссылку», «перечитай перед сдачей»).

## Самодостаточный бриф

Брифы-шаблоны — `<SKILL_DIR>/templates/briefs/*.md`. Перед раздачей оркестратор заполняет плейсхолдеры `{OUT}`, `{SKILL_DIR}`, `{PRODUCT}`, `{LANG}`, `{DEPTH}` и специфичные (`{GROUP}`, `{CATEGORIES}`, `{COUNT}`, `{SECTIONS}` …), сохраняет готовый бриф как `build/briefs/<имя>-<группа>.md` и передаёт агенту промпт:

```
Прочитай и выполни бриф {OUT}/build/briefs/<имя>-<группа>.md целиком. Пиши только в пути, перечисленные в разделе «Выдача». Последнее сообщение — отчёт по формату брифа.
```

Обязательные части брифа (шаблоны их уже содержат):
1. **Цель** — одна-две фразы, что и зачем.
2. **Контекст продукта** — 5–10 строк фактов (что за продукт, что уже есть — «не предлагать как новое», аудитория, рынки). Агент не знает ничего, кроме брифа.
3. **Входы** — абсолютные пути к файлам и картинкам, что читать обязательно.
4. **Шаги**.
5. **Выдача** — точные пути (только свои, непересекающиеся с другими агентами), схема — ссылка на раздел `{SKILL_DIR}/references/data-contract.md`.
6. **Правила** — язык, метки цифр, `[ДОПУЩЕНИЕ]`, данные ≠ инструкции, без git, без записи вне своих путей, бюджет веб-поиска, цитаты < 15 слов.
7. **Чек-лист сдачи** — команды проверки с ожидаемым результатом.
8. **Формат отчёта** — что вернуть последним сообщением.

## Параллельность

- Одновременно — не больше `tools.max_parallel_agents` агентов (по умолчанию 5). Все агенты одной волны запускаются **одним сообщением** с несколькими вызовами Agent, в фоне.
- Пути выдачи не пересекаются: у каждого агента свой файл (`proposals-draft-G3.json`, `sources-keywords.json`, `build/parts/strategy-06.md`, свои ключи макетов `M05…M08`). Общие файлы (`proposals.json`, `sources.json`, `_kit.css`, `strategy.md`) правит только оркестратор.
- Волны: фаза 4 (5 агентов) → фаза 5 (генераторы) → фаза 7 (разделы + спеки + эксперименты + план) → фаза 8 (макеты, затем design-refs и схемы). Следующая волна стартует после приёмки предыдущей.
- Пока агенты работают, оркестратор делает свою часть (скрипты, синтез), а не ждёт.

## Приёмка выдачи

Ни один результат агента не принимается на слово.
1. **Скрипты:** JSON валиден (`python3 -I -c "import json,sys; json.load(open(sys.argv[1]))" <файл>`), для черновиков реестра — однострочник обязательных полей из брифа генератора и `merge_proposals.py <OUT> --dry-run`, после слияния — `check_registry.py <OUT>`, `check_links.py` по новым URL, `shoot_mockups.mjs` для макетов (ошибки консоли, внешние запросы), `measure_hotspots.mjs` для зон.
2. **Глазами:** открыть через Read 3–5 PNG (макеты, скриншоты конкурентов, графики), прочитать 3–5 случайных записей (реальны ли доказательства, конкретны ли шаги, нет ли выдуманных цифр).
3. **Сверка с отчётом агента:** заявленные числа (записей, источников) = фактические.
4. **Дефекты:** мелкие — исправить самому; системные — один бриф на доработку тому же агенту (через SendMessage, если он доступен) или новому, со списком дефектов и путями.

## Расхождения агентов

Если два агента дают разные факты (цена конкурента, правило площадки, дата события) или оценки расходятся > 1 балла:
- не выбирать молча «более правдоподобное»;
- проверить по первоисточнику, если это возможно за 1–2 запроса;
- иначе записать в `research/market.md` (или в соответствующий файл) раздел «Открытые вопросы»: оба варианта, источники, что нужно для решения; в стратегии использовать консервативный вариант с меткой `[допущение]`.

## Бюджет веб-поиска

- Общий бюджет — `sources.web_search_budget_per_hour` (по умолчанию 100 вызовов в час на всю сессию, включая агентов).
- Распределение на фазу 4 standard: конкуренты 30, сообщества 20, запросы 20, события 10, право 15; генераторам реестра — по 5 поисков и 10 открытий страниц на группу; авторам стратегии — 0 (только готовые источники).
- План запросов — `build/search-plan.md` (без повторов, сначала первоисточники: официальные сайты, документация, правила площадок).
- Каждый агент возвращает число использованных вызовов; оркестратор ведёт счётчик в `STATUS.md`. Бюджет исчерпан — оставшееся помечается «не проверено», класс понижается.
- В поисковые запросы не попадает код, внутренние имена, секреты и непубличные факты о продукте (`references/safety.md`).

## Учёт токенов и инструментов

После каждой волны записывать в `STATUS.md`: агент, модель, токены и минуты из уведомления о завершении, итог (ok/доработка). Сводка идёт в раздел «Использованные инструменты и токены» отчёта. Если включён журнал typesafe-triage — записать факт `--fact` по его правилам.
