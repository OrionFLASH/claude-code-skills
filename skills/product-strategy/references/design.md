# Дизайн-часть: токены, макеты, референсы

Пути — `references/data-contract.md` (`mockups/`, `design-refs/`, `data/mockups-index.json`, `design-refs/NN-slug.json`).

## 1. Токены из продукта

1. `node <SKILL_DIR>/scripts/node/audit_site.mjs <URL> <OUT> --mobile --themes light,dark` снимает CSS custom properties из `:root` и из тёмной темы (`[data-theme=dark]`, `prefers-color-scheme`) и computed CSS ключевых экранов и пишет `mockups/tokens.css` — **обе темы**: светлые значения в `:root`, тёмные в `[data-theme="dark"]`. Частотный анализ — запасной путь, если своих переменных у продукта нет. Состав: цвета (фон, поверхность, текст, приглушённый текст, акцент, успех/ошибка), шрифты (семейство, размеры, начертания), радиусы, тени, отступы, размеры кнопок и полей.
2. Проверить файл глазами: акцент — это действительно цвет бренда, а не цвет случайной ссылки; нет 20 почти одинаковых серых (свести к 3–5); у каждой переменной есть пара в тёмной теме (или тёмной темы у продукта нет — записать).
3. Нет веб-интерфейса или аудит не прошёл — токены из исходников (CSS/темы/`tailwind.config`, ресурсы приложения, иконка/логотип) или нейтральная палитра; записать в `ui-inventory.md`, откуда взяты.
4. Токены — единая палитра для макетов, графиков (`charts.py`) и веб-страницы. Палитра графиков дополнительно проверяется на различимость для дальтоников (порядок цветов, а не только оттенок).

## 2. Дизайн-язык сначала, макеты потом

Стартовый набор поставляется со скиллом: `<SKILL_DIR>/templates/mockup-kit/` (`_kit.css`, `_base.html`) — с исправлениями дефектов, найденных в реальных прогонах (бейдж концепта над мобильной нижней панелью, `nowrap` у бейджей, контраст опасной кнопки, штриховка замка, позиционирование подсказок), обеими темами и типовыми контролами (сегментный переключатель, чипы фильтра, тумблер, чекбокс, мобильная нижняя панель). **Набор не пишется с нуля** ни оркестратором, ни агентами.

Сразу после фазы 6 (до текстов стратегии — см. «Порядок фаз 7 и 8» в `references/phases.md`) оркестратор (opus):
- копирует набор в `mockups/concepts/` и подставляет токены продукта из `tokens.css` (обе темы);
- `mockups/concepts/_kit.css` — переменные из `tokens.css` + компоненты продукта: шапка/навигация, кнопки (основная, вторичная, ссылка), поля, карточки, модалка, таблица, бейджи, пустое состояние, тост, мобильная шапка и нижняя панель, бейдж концепта `.ps-concept-badge`, выноска `.ps-tip`. Классы с префиксом `ps-`, чтобы не конфликтовать с классами макетов.
- `mockups/concepts/_kit.js` — только если нужны повторяющиеся куски (шапка, панель) — вставка по `data-*` атрибутам (атрибуты в нижнем регистре через дефис: HTML приводит имена к нижнему регистру).
- `mockups/concepts/_base.html` — демо-экран, где использованы все компоненты; рендер `shoot_mockups.mjs` в обеих темах и просмотр PNG через Read **до** раздачи. Ошибки в наборе дешевле исправить один раз, чем в 15 макетах; баги, о которых сообщили агенты, исправляет оркестратор в `_kit.css` (и, если они шаблонные, — сообщает разработчикам скилла для `templates/mockup-kit/`).
- в бриф макетов — список классов набора (`{KIT_CLASSES}`), чтобы агенты не изобретали свои аналоги.
- Если владелец дал референсный редизайн (Issue, макет, скриншоты) — набор строится по нему, а не по текущему сайту; в отчёте указать, что макеты в новом стиле.

## 3. Правила макетов

- **Детально, в стиле продукта**: реальные компоненты из набора, правдоподобные тексты на языке продукта, реалистичные данные (вымышленные, но правдоподобные; без персональных данных реальных людей). Схематичные «серые прямоугольники» — только если контекст требует схемы.
- **Один макет — одна идея** (одно или несколько связанных предложений), видно главное действие. Выноски-пояснения допустимы, оформляются как часть набора (`ps-tip`).
- **Бейдж «Концепт, не существующая функция»** на каждом макете (виден на скриншоте, не перекрывает главное): текст бейджа — «Концепт, не существующая функция · <продукт> · <дата>».
- **Скриншоты «Текущее состояние»** (`mockups/current/*.png`) — факт аудита: не заменять концептами, не перерисовывать, подписывать «Текущее состояние, <дата>».
- **Существующее не выдавать за новое**: элементы, которые уже есть в продукте, на макете остаются как есть; новое — явно новое (в design-refs — `state: new|changed|shared`).
- **Чужие материалы:** не копировать защищённые изображения, логотипы, иллюстрации, тексты конкурентов; не использовать товарные знаки так, будто это наш продукт. Ассеты продукта владельца (логотип, иконки из репозитория) — можно. Игровые/медиа-ассеты третьих лиц — только для внутреннего обсуждения, с пометкой IP-риска в отчёте.
- **Офлайн:** никаких внешних шрифтов/CDN/изображений по сети — только локальные файлы рядом с макетом (`shoot_mockups.mjs` считает внешние запросы ошибкой).
- **Размеры:** десктоп 1440×900, мобильный 390×844 (`<html data-viewport="mobile">` — по этому атрибуту `shoot_mockups.mjs` сам находит макет и его размер); макет не выходит за экран (нет горизонтальной прокрутки), если это не страница с прокруткой по замыслу — тогда указать высоту.
- **Контраст** текста ≥ 4,5:1 (крупный ≥ 3:1) **в обеих темах** — включая бейджи, кнопки-предупреждения (белый на красном легко оказывается 4,49:1), текст на штриховке и на полупрозрачных панелях; фокус виден, кликабельные зоны ≥ 24×24 CSS-пикселя. Полупрозрачные поверхности — проверять контраст над самым светлым и самым тёмным фоном под ними; где много мелкого текста — плотная поверхность.
- **Имена:** `mockups/concepts/Mxx-<slug>.html`, ключ `Mxx-<slug>` = ключ в `data/mockups-index.json` и в `![[mockup:…]]`.
- **Состояния:** где важно — гость/бесплатный/платный, пустое/заполненное, ошибка; можно двумя экранами рядом в одном макете.

## 4. Макеты для продуктов без GUI

| Продукт | Вместо экрана |
|---|---|
| CLI | «терминал» в HTML: моноширинный шрифт, цвета из темы терминала продукта (или нейтральные), реалистичный вывод команды, подсказки, ошибки с исправлением; prompt без реальных путей пользователя |
| Библиотека/SDK | страница документации в стиле сайта документации проекта: пример кода «до/после», блок quickstart, таблица API |
| API | схема вызовов (последовательность запросов), пример запроса/ответа, страница портала разработчика |
| Бот | экран чата мессенджера (нейтральная стилизация, без логотипов платформы) с диалогом бота |
| Расширение/плагин | всплывающее окно расширения поверх условной страницы `example.com` |
| Фоновый сервис | дашборд статуса/настроек или письмо-уведомление |

## 5. Проверка макетов

1. `node <SKILL_DIR>/scripts/node/shoot_mockups.mjs <OUT>` — **автообнаружение** `mockups/concepts/*.html` (ключ — имя файла, viewport — `data-viewport`; служебные `_base`, `_kit` пропускаются) → PNG рядом с HTML, `data/mockups-index.json` и агрегат `data/mockups-check.json` (ошибки консоли, внешние запросы, переполнение). Агенты запускают `--only <ключ>` → `data/mockups-check.<ключ>.json` и общий индекс не трогают; оркестратор после волны — без `--only`.
2. Каждый PNG — через Read: ничего не обрезано, нет наложений, бейдж виден, текст читается, нет «lorem ipsum».
3. Поиск запрещённого: старые элементы, которые заказчик просил убрать; внешние URL (`grep -E 'https?://' mockups/concepts/*.html` — только `example.com` в тексте допустим).
4. Связь с реестром: у каждого макета `proposals` не пустой; обратную ссылку `mockup`/`mockups` у предложений ставит `python3 <SKILL_DIR>/scripts/link_mockups.py <OUT>` (не вручную).

## 6. design-refs: карточки для постановки задач

Цель — владелец заводит задачи на интерфейс, не читая стратегию. Карточка на каждый макет (+ `00-…` «общий дизайн-язык» на deep/exhaustive, если набор новый).

Файлы на экран:
- `design-refs/NN-slug.png` — копия PNG макета;
- `design-refs/NN-slug.md` — по шаблону `templates/design-ref-card.md` (Что это / Как выглядит / Как взаимодействовать / Что нужно доделать / Элементы / Открытые вопросы);
- `design-refs/NN-slug.json` — схема в контракте (`file`, `png`, `scale`, `width`, `height`, `title`, `proposals`, `kind: page|mobile|component|external`, `summary`, `entry`, `shared`, `new_elements`, `hotspots[]`, `todo[]`, `questions[]`).

Hotspots:
- Измерять, а не на глаз: `node <SKILL_DIR>/scripts/node/measure_hotspots.mjs <OUT> …` (Playwright открывает макет в его viewport и берёт `getBoundingClientRect()` по селекторам). Координаты — CSS-пиксели исходного размера; для PNG, снятого в 2×, `scale: 2`.
- Проверять глазами: `measure_hotspots.mjs … --draw <png>` рисует пронумерованные рамки зон поверх макета; результат — во временную папку и через Read. Свои скрипты наложения не нужны.
- 5–10 зон на экран: главный объект, ключевые кнопки, новые элементы, 1–2 зоны общего дизайна. Зоны внутри экрана, мелкие расширять до 24 px, `n` уникальны и совпадают с нумерацией «Элементы» в `.md`.
- `state`: `new` — новый элемент; `changed` — существующий в новом виде; `shared` — часть общего дизайн-языка (описан в карточке 00).
- `design-refs/README.md` собирает `python3 <SKILL_DIR>/scripts/build_design_refs_readme.py <OUT>`: таблица карточек (№, файл, вид, предложения, число зон, PNG, кратко), общие элементы, открытые вопросы, порядок постановки задач по `dep_rank`, как перемерить зоны после правки макета. Ручной README скрипт не затирает (`README.generated.md`, `--force`).

## 7. Референсные дизайны конкурентов

В разделе конкурентов и в `data/competitors.json → best_solutions, design_note`:
- **Что взять:** паттерн (например, «предпросмотр платной функции с размытием», «пустое состояние с примером»), а не внешний вид. Описать словами: где на экране, как работает, почему удачно, как это адаптировать к нашему продукту и токенам.
- **Как показать:** скриншот конкурента из `competitors/shots/` как цитата-иллюстрация с подписью «<Конкурент>, <дата снимка>, источник: <URL>»; не обрезать так, чтобы скрыть принадлежность.
- **Без копирования:** макеты по мотивам паттерна рисуются нашими компонентами и токенами; тексты — свои; логотипы и иллюстрации конкурента в макеты не попадают.
- **Что не брать:** тёмные паттерны (скрытая отмена, принудительная подписка, фальшивые таймеры), даже если они у лидера рынка; указать в `avoid`.
