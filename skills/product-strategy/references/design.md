# Дизайн-часть: токены, макеты, референсы

Пути — `references/data-contract.md` (`mockups/`, `design-refs/`, `data/mockups-index.json`, `design-refs/NN-slug.json`).

## 1. Токены из продукта

1. `node <SKILL_DIR>/scripts/node/audit_site.mjs <URL> <OUT> --mobile --themes light,dark` снимает CSS custom properties из `:root` и из тёмной темы (`[data-theme=dark]`, `prefers-color-scheme`) и computed CSS ключевых экранов и пишет `mockups/tokens.css` — **обе темы**: светлые значения в `:root`, тёмные в `[data-theme="dark"]`. Частотный анализ — запасной путь, если своих переменных у продукта нет. Состав: цвета (фон, поверхность, текст, приглушённый текст, акцент, успех/ошибка), шрифты (семейство, размеры, начертания), радиусы, тени, отступы, размеры кнопок и полей.
2. Проверить файл глазами: акцент — это действительно цвет бренда, а не цвет случайной ссылки; нет 20 почти одинаковых серых (свести к 3–5); у каждой переменной есть пара в тёмной теме (или тёмной темы у продукта нет — записать).
3. Нет веб-интерфейса или аудит не прошёл — токены из исходников (CSS/темы/`tailwind.config`, ресурсы приложения, иконка/логотип) или нейтральная палитра; записать в `ui-inventory.md`, откуда взяты.
4. Токены — единая палитра для макетов, графиков (`charts.py`) и веб-страницы. Палитра графиков дополнительно проверяется на различимость для дальтоников (порядок цветов, а не только оттенок).

## 2. Дизайн-язык сначала, макеты потом

Стартовый набор поставляется со скиллом: `<SKILL_DIR>/templates/mockup-kit/` (`_kit.css`, `_icons.css`, `_base.html`; мобильный слой `mobile/_mobile.css`, `_base-mobile.html`, `_storyboard.html`) — с исправлениями дефектов, найденных в реальных прогонах (бейдж концепта над мобильной нижней панелью, `nowrap` у бейджей, контраст опасной кнопки, штриховка замка, позиционирование подсказок), обеими темами и типовыми контролами (сегментный переключатель, чипы фильтра, тумблер, чекбокс, мобильная нижняя панель). **Набор не пишется с нуля** ни оркестратором, ни агентами.

Сразу после фазы 6 (до текстов стратегии — см. «Порядок фаз 7 и 8» в `references/phases.md`) оркестратор (opus):
- **копирует набор скриптом** `python3 <SKILL_DIR>/scripts/mockup_kit.py init <OUT> [--forms web,mobile|mobile-later] [--modes …]` — однократно, идемпотентно, до волны макетов: файлы набора, `M00-design-language.html` (демо всех форм продукта: веб и мобильный на одной странице), пустой `tokens.css`, заготовки `tokens-<режим>.css`, замок `build/kit.lock`. Агенты набор не копируют (раньше параллельные агенты устраивали гонку); после волны — `mockup_kit.py verify <OUT>` (код 1 — кто-то изменил набор; осознанная правка оркестратора — `--update`). Токены продукта — из `tokens.css` (обе темы). **Выбор по `run-config.product.type`:** `mobile` (и мобильные экраны любого продукта) — `_kit.css` + `_icons.css` + `mobile/_mobile.css`, эталоны `mobile/_base-mobile.html`, `mobile/_storyboard.html`, демо `mobile/kit-demo-mobile.html` → `_kit-demo-mobile.html`; веб-приложение, сайт, дашборд, `desktop` — `_kit.css` + `_icons.css`, эталон `_base.html`, демо `kit-demo.html` → `_kit-demo.html`; смешанный — оба;
- `tokens.css`, написанный вручную (нет сайта для `audit_site.mjs`), может не содержать `--c-*`: набор строит мост сам из `--primary`, `--bg`, `--surface`/`--card`, `--text`, `--muted`, `--border`, `--on-primary`, `--success`, `--warning`, `--danger` (список — README набора). Если для роли нет ни `--c-*`, ни имени моста, набор рисует запасной палитрой, а `shoot_mockups.mjs` громко сообщает «использован запасной цвет набора» (FAIL, если у продукта есть свои переменные);
- `mockups/concepts/_kit.css` — переменные из `tokens.css` + компоненты продукта: шапка/навигация, кнопки (основная, вторичная, ссылка), поля, карточки, модалка, таблица, бейджи, пустое состояние, тост, мобильная шапка и нижняя панель, бейдж концепта `.ps-concept-badge`, выноска `.ps-tip`. Классы с префиксом `ps-`, чтобы не конфликтовать с классами макетов.
- `mockups/concepts/_kit.js` — только если нужны повторяющиеся куски (шапка, панель) — вставка по `data-*` атрибутам (атрибуты в нижнем регистре через дефис: HTML приводит имена к нижнему регистру).
- `mockups/concepts/_base.html` (`_base-mobile.html`, `_storyboard.html`) — эталонные экраны, `_kit-demo*.html` — все компоненты; рендер `shoot_mockups.mjs <OUT> --kit` (обе темы, проверка контраста и запасных цветов) и просмотр PNG через Read **до** раздачи; `--kit` пишет `_base.png`, `_base-mobile.png` и т. д. — на эти PNG ссылается бриф макетов. Ошибки в наборе дешевле исправить один раз, чем в 15 макетах; баги, о которых сообщили агенты, исправляет оркестратор в `_kit.css` (и, если они шаблонные, — сообщает разработчикам скилла для `templates/mockup-kit/`).
- в бриф макетов — список классов набора (`{KIT_CLASSES}`), чтобы агенты не изобретали свои аналоги.
- Если владелец дал референсный редизайн (Issue, макет, скриншоты) — набор строится по нему, а не по текущему сайту; в отчёте указать, что макеты в новом стиле.

## 2.1. Дизайн-этап режима идеи (C8): направления, выбор, режимы, галерея

Параметры — `run-config.design` (пишет опрос; `mockup_kit.py params <OUT>`): `directions_count` (по умолчанию 3; владелец может попросить 1–7), `modes[]` и `default_mode`, `forms[]` (`web`, `mobile`, `mobile-later`), `pointer_first`, `gallery`, `chosen`, `chosen_by` (`owner` | `default`).
- **C8a → C8-ask → C8b.** C8a — агент пишет `design/directions.md` (заголовки `## Направление A — «…»`, раздел `## Рекомендация`) и, если вариантов больше одного, по 2–3 рабочих экрана одного сценария на каждый. C8-ask — оркестратор: `mockup_kit.py directions <OUT>` (рекомендованное первым) → AskUserQuestion владельцу (+ ссылка на галерею) → `mockup_kit.py choose <OUT> --direction <id> --by owner`. C8b — токены и макеты выбранного направления. **Вне автопилота шаги 2–3 брифа `concept-design` без `design.chosen` не рендерятся** (`mockup_kit.py gate <OUT> --steps 2-3` → код 3; функция `design_gate()` для `render_brief.py`); в автопилоте — `choose --recommended --by default`. REPORT показывает, кто выбрал направление (`design.chosen_by`).
- **Направления различаются компоновкой и метафорой, а не цветом**: своя схема экрана (плотные панели / плитки / мастер / лента / холст), своя метафора и плотность.
- **Режимы интерфейса** — компоновки одной дизайн-системы на общих данных: правила переключения, режим по умолчанию (вопрос владельцу), очередь/горизонт каждого режима. Токены — «набор на режим»: общий `tokens.css` + `tokens-<режим>.css` (`--c-*` под `[data-mode="<режим>"]`), макет — `<html data-mode="…">`.
- **Галерея** `mockups/gallery.html` — стандартный артефакт показа вариантов: `mockup_kit.py gallery <OUT>` по атрибутам макетов `data-variant`, `data-screen-id` (один сценарий во всех вариантах — таблица сравнения), `data-variant-note`, `data-variant-status="rejected"`. Меньше 2 экранов у варианта — предупреждение и код 1.
- **Мобильный задел.** Владелец сказал «мобильное позже» (`forms` содержит `mobile-later`, `design.mobile_reserve`) — спутниковая серия 1–2 мобильных экранов `Mxx-m-<slug>` на `_base-mobile.html`; это не обещание мобильного приложения в MVP.
- **Канон демо-данных** `data/demo-canon.json` (если есть) — единственный источник имён и чисел на макетах всех агентов.

## 3. Правила макетов

- **Детально, в стиле продукта**: реальные компоненты из набора, правдоподобные тексты на языке продукта, реалистичные данные (вымышленные, но правдоподобные; без персональных данных реальных людей). Схематичные «серые прямоугольники» — только если контекст требует схемы.
- **Один макет — одна идея** (одно или несколько связанных предложений), видно главное действие. Выноски-пояснения допустимы, оформляются как часть набора (`ps-tip`).
- **Бейдж «Концепт, не существующая функция»** на каждом макете (виден на скриншоте, не перекрывает главное): текст — одна константа «Концепт, не существующая функция · <продукт> · <дата>» (и в режиме идеи), элемент — с классом `.ps-concept-badge`; телефон — `is-strip` первым элементом `.pm-phone` (текст не обрезается: не влезает — убрать дату, затем название), десктоп с нижней панелью — `is-above-nav`, длинная страница — `is-inline` (таблица — README набора). `shoot_mockups.mjs` ищет бейдж по классу и считает обрезанный текст замечанием.
- **Подсветка элементов** — стандарт макета: 12–25 элементов с `data-hs`, `data-hs-title`, `data-hs-what` («что это»), `data-hs-why` («для чего»), `data-hs-p` (P-id), `data-hs-sec` (разделы) + `<script src="_hotspots.js"></script>`; зоны для страницы — `data/mockups-check.<ключ>.json → hotspots.zones`.
- **Пробелы и расхождения с реестром** — строками `НУЖНО-ПРЕДЛОЖЕНИЕ: <заголовок> | <категория> | <P-id>` и `РАСХОЖДЕНИЕ: <P-id> | <Mxx> | <суть>` (в `design-refs/*.md` — «Открытые вопросы», в макете — комментарием `<!-- … -->`). После C8: `link_mockups.py <OUT> --collect-gaps` → черновики `data/proposals-draft-G8.json` (`needs_details: true`) и записи `data/fact-check.json` (`kind: mockup_vs_registry`), итог `build/collect-gaps.json` (числа для REPORT); затем оценки черновиков, `merge_proposals.py --append G8` и `link_mockups.py <OUT> --remap-drafts` (G8-NN в макетах → P-id по `build/id-map.json`).
- **Скриншоты «Текущее состояние»** (`mockups/current/*.png`) — факт аудита: не заменять концептами, не перерисовывать, подписывать «Текущее состояние, <дата>».
- **Существующее не выдавать за новое**: элементы, которые уже есть в продукте, на макете остаются как есть; новое — явно новое (в design-refs — `state: new|changed|shared`).
- **Чужие материалы:** не копировать защищённые изображения, логотипы, иллюстрации, тексты конкурентов; не использовать товарные знаки так, будто это наш продукт. Ассеты продукта владельца (логотип, иконки из репозитория) — можно. Игровые/медиа-ассеты третьих лиц — только для внутреннего обсуждения, с пометкой IP-риска в отчёте.
- **Офлайн:** никаких внешних шрифтов/CDN/изображений по сети — только локальные файлы рядом с макетом (`shoot_mockups.mjs` считает внешние запросы ошибкой).
- **Размеры:** десктоп 1440×900, мобильный 390×844 (`<html data-viewport="390x844">` или `<meta name="ps:viewport">` — по ним `shoot_mockups.mjs` сам находит макет и его размер); раскадровка мобильных экранов — 2–4 телефона в ряд с подписями (`_storyboard.html`): 4 — `1720x1000`, 3 — `1320x1000`, 2 — `900x1000`, высота **≥ 960–1000** (при 900 подписи под телефонами обрезаются; раскадровка выше viewport — замечание `shoot_mockups`). Макет не выходит за экран (нет горизонтальной прокрутки); страница с прокруткой по замыслу — снимать с `--full-page`.
- **Бейдж на полном снимке:** `position: fixed` уезжает в низ полностраничного PNG — на длинных страницах и раскадровках `.ps-concept-badge.is-inline`, внутри телефона — `.is-strip`.
- **Контраст** текста ≥ 4,5:1 (крупный ≥ 3:1) **в обеих темах** — включая бейджи, кнопки-предупреждения (белый на красном легко оказывается 4,49:1), текст на штриховке и на полупрозрачных панелях; фокус виден, кликабельные зоны ≥ 24×24 CSS-пикселя. Полупрозрачные поверхности — проверять контраст над самым светлым и самым тёмным фоном под ними; где много мелкого текста — плотная поверхность.
- **Имена:** `mockups/concepts/Mxx-<slug>.html`, ключ `Mxx-<slug>` = ключ в `data/mockups-index.json` и в `![[mockup:…]]`.
- **Состояния:** где важно — гость/бесплатный/платный, пустое/заполненное, ошибка; можно двумя экранами рядом в одном макете.

## 3.1. Принцип взаимодействия: pointer/touch-first

Кнопки, мышь и касание — основной путь; клавиатура — ускорение (подсказка `kbd.ps-kbd` рядом с видимой кнопкой, не вместо неё). Цели нажатия ≥ 32 px для мыши и ≥ 44 px для касания (набор держит через `--k-target`), перетаскивание всегда дублируется кнопками (`data-drag-alt="<селектор кнопок>"`), на телефоне — нижние вкладки и действия в зоне большого пальца, жесты — только с видимой альтернативой. Автопроверка — `shoot_mockups.mjs --targets` (сама включается при `design.pointer_first` и в `--kit`): мелкие цели (ссылки внутри строки текста — исключение WCAG 2.5.8), перетаскивание без кнопок; мобильные макеты снимаются с эмуляцией касания.

| Фоновый сервис | дашборд статуса/настроек или письмо-уведомление |

## 5. Проверка макетов

1. `node <SKILL_DIR>/scripts/node/shoot_mockups.mjs <OUT>` — **автообнаружение** `mockups/concepts/*.html` (ключ — имя файла; `viewport`, `title`, `proposals`, `kind` — из атрибутов `<html>` или `<meta name="ps:…">`; служебные `_*.html` пропускаются) → PNG рядом с HTML, `data/mockups-index.json` (слияние по ключу; записи `discovered: true` обновляются из HTML при каждом запуске, ручные — нет) и агрегат `data/mockups-check.json` (ошибки консоли, внешние запросы, переполнение, запасные цвета, высота раскадровок; `--contrast` — ещё и контраст). Агенты запускают `--only <ключ>` → только `data/mockups-check.<ключ>.json`: с `--only` (и `--no-index`) общие `mockups-index.json` и `mockups-check.json` **не пишутся**; оркестратор после волны — без `--only`.
2. Каждый PNG — через Read: ничего не обрезано, нет наложений, бейдж виден, текст читается, нет «lorem ipsum».
3. Поиск запрещённого: старые элементы, которые заказчик просил убрать; внешние URL (`grep -E 'https?://' mockups/concepts/*.html` — только `example.com` в тексте допустим).
4. Связь с реестром: у каждого макета `proposals` не пустой; обратную ссылку `mockup`/`mockups` у предложений ставит `python3 <SKILL_DIR>/scripts/link_mockups.py <OUT>` (не вручную). Служебные макеты и карточки (`kind: component` или `links: false`, файлы `_*.html`) — общий дизайн-язык, демо набора — с предложениями не связываются.
5. Флаги проверки 1.5: `--contrast` учитывает текст в SVG (цвет — `fill`) и заливку SVG-фигур под текстом; `--other-theme` снимает вторую тему (`<ключ>.theme-<тема>.png`, её переполнение, контраст и запасные цвета — замечания); `--layout` — дети, вылезающие из однострочных flex-рядов, и скрытая прокрутка (обрезанные кнопки сегментов и чипов); `--targets[=pointer|touch]`; `--hotspots N`. `--only` принимает макеты с черновыми id `G8-xx` в `data-proposals`; поле `date` — локальная дата. `link_mockups.py <OUT> --index-only` — индекс макетов без браузера (заранее, до снимков: для specs и брифов).
6. Блок-схемы: `node <SKILL_DIR>/scripts/node/check_flow.mjs <OUT> [--draw <временная папка>]` — пересечения блоков (`data-node`), подписи за рамкой блока, наложение подписей, подписи стрелок на чужих блоках, обрезка по краю → `data/flows-check.json`; `--draw` рисует замечания красными рамками (смотреть через Read).

## 6. design-refs: карточки для постановки задач

Цель — владелец заводит задачи на интерфейс, не читая стратегию. Карточка на каждый макет (+ `00-…` «общий дизайн-язык» на deep/exhaustive, если набор новый). Карточка 00 ссылается на `mockups/concepts/M00-design-language.html` — демо всех форм продукта, которое создаёт `mockup_kit.py init` (атрибут `data-kind="kit"` демо превращается в `kind: component` индекса; `_base.html` для этого не годится — служебные `_*.html` в индекс не попадают); в карточке `"kind": "component"`, `shared` — полный список общих элементов (из него `build_design_refs_readme.py` строит справочник `build/shared-elements.json`; остальные карточки берут имена `shared` только из него).

Файлы на экран:
- `design-refs/NN-slug.png` — копия PNG макета;
- `design-refs/NN-slug.md` — по шаблону `templates/design-ref-card.md` (Что это / Как выглядит / Как взаимодействовать / Что нужно доделать / Элементы / Открытые вопросы);
- `design-refs/NN-slug.json` — схема в контракте (`file`, `png`, `scale`, `width`, `height`, `title`, `proposals`, `kind: page|mobile|component|external`, `summary`, `entry`, `shared`, `new_elements`, `hotspots[]`, `todo[]`, `questions[]`).

Hotspots:
- Измерять, а не на глаз: `node <SKILL_DIR>/scripts/node/measure_hotspots.mjs <OUT> …` (Playwright открывает макет в его viewport и берёт `getBoundingClientRect()` по селекторам). Координаты — CSS-пиксели исходного размера от угла всего PNG; для PNG, снятого в 2×, `scale: 2`. Раскадровка: у зоны `screen` — номер кадра (из `data-screen` или порядка `.pm-frame`; `--draw` подписывает «n·кN»). Длинная страница: `--full-page` — координаты от начала страницы, `height` = высота страницы, окно — в `viewport` карточки.
- Проверять глазами: `measure_hotspots.mjs … --draw <png>` рисует пронумерованные рамки зон поверх макета; результат — во временную папку и через Read. Свои скрипты наложения не нужны.
- 5–10 зон на экран: главный объект, ключевые кнопки, новые элементы, 1–2 зоны общего дизайна. Зоны внутри экрана, мелкие расширять до 24 px, `n` уникальны и совпадают с нумерацией «Элементы» в `.md`.
- `state`: `new` — новый элемент; `changed` — существующий в новом виде; `shared` — часть общего дизайн-языка (описан в карточке 00).
- `design-refs/README.md` собирает `python3 <SKILL_DIR>/scripts/build_design_refs_readme.py <OUT>`: таблица карточек (№, файл, вид, предложения, число зон, PNG, кратко), общие элементы (одинаковые по смыслу имена — одной строкой; имена не из справочника — отдельным списком и предупреждением), открытые вопросы, порядок постановки задач по `dep_rank`, как перемерить зоны после правки макета. Ручной README скрипт не затирает (`README.generated.md`, `--force`). README и справочник пишет только скрипт — агенты design-refs их не трогают, какой бы диапазон им ни достался.

## 7. Референсные дизайны конкурентов

В разделе конкурентов и в `data/competitors.json → best_solutions, design_note`:
- **Что взять:** паттерн (например, «предпросмотр платной функции с размытием», «пустое состояние с примером»), а не внешний вид. Описать словами: где на экране, как работает, почему удачно, как это адаптировать к нашему продукту и токенам.
- **Как показать:** скриншот конкурента из `competitors/shots/` как цитата-иллюстрация с подписью «<Конкурент>, <дата снимка>, источник: <URL>»; не обрезать так, чтобы скрыть принадлежность.
- **Без копирования:** макеты по мотивам паттерна рисуются нашими компонентами и токенами; тексты — свои; логотипы и иллюстрации конкурента в макеты не попадают.
- **Что не брать:** тёмные паттерны (скрытая отмена, принудительная подписка, фальшивые таймеры), даже если они у лидера рынка; указать в `avoid`.
