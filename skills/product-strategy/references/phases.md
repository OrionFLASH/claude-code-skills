# Фазы прогона 0–9

Пути и схемы — `references/data-contract.md`. Формулы оценок — `references/scoring.md`. Якоря шкал — `references/methodology-anchors.md`. Кто что делает — `references/orchestration.md`. Python-скрипты — `python3 <SKILL_DIR>/scripts/<имя>.py`, node-скрипты — `node <SKILL_DIR>/scripts/node/<имя>.mjs`; позиционный аргумент обычно `<OUT>` (исключения указаны ниже); точные флаги — `--help` каждого скрипта.

Сквозные правила:
- Конфиг прогона — `<OUT>/build/run-config.json`. Глубина `strategy.depth`, объёмы `scope.*`, минимум предложений `strategy.proposals_min`, параллельность `tools.max_parallel_agents`. Если значение из таблицы глубины ниже расходится с конфигом — **побеждает конфиг**.
- Код репозитория не меняется. Пишем только в `<OUT>` (и, если `output.inside_repo`, коммитим только `<OUT>` в ветке `output.git_branch`).
- Догадки помечаются `[ДОПУЩЕНИЕ]` и сразу дописываются в `run-config.json → assumptions` и в черновик `research/questions-owner.md` (итог — не больше 10 вопросов).
- Чек-лист фаз — в `<OUT>/build/STATUS.md` (создаёт `init_run.py`; отметить фазу — `init_run.py <OUT> --done N`, дописать чекпоинт — `init_run.py <OUT> --status "…"`, показать — `--show`). Подробный чек-лист шагов — `<OUT>/TASKS.md` (пункт на каждый шаг; отмечать сразу). Чекпоинт — после **каждой** фазы, содержание:

```markdown
## Фаза N. <название> — готово <YYYY-MM-DD HH:MM>
- Артефакты: <пути, число записей>
- Проверки: <команда → результат>
- Допущения: <новые за фазу>
- Пропущено/сокращено: <что и почему>
- Следующий шаг: <первая команда следующей фазы>
```

После обрыва сессии: прочитать `TASKS.md` и `STATUS.md`, продолжить с первого открытого пункта, не переделывать готовое.

## Фаза 0. Подготовка

**Цель:** папка прогона, ветка, чек-лист, работающие инструменты, понятные границы.
**Входы:** `build/run-config.json` (после `intake.py`), репозиторий.
**Шаги:**
1. `python3 <SKILL_DIR>/scripts/skill_dir.py` — запомнить `<SKILL_DIR>`.
2. `python3 <SKILL_DIR>/scripts/init_run.py <OUT>` — структура папок по контракту, `build/STATUS.md` с чек-листом фаз, `.gitignore` для node-модулей. Брифы оркестратор заполняет позже из `<SKILL_DIR>/templates/briefs/` и сохраняет в `build/briefs/`.
3. Git: снять `git status --porcelain` репозитория в `build/git-status-before.txt`. Если `output.inside_repo` — создать ветку `output.git_branch` от основной **до первой записи**; иначе ветка не нужна.
4. `python3 <SKILL_DIR>/scripts/check_env.py --out <OUT> --json <OUT>/build/env.json --session-skills <скиллы сессии через запятую>` (Python, Node, Playwright + Chromium, `gh` и его авторизация, TypeSafe-ключ в окружении, доступные скиллы); `--plan` — что ставить, `--install-node <OUT>` — Node-модули локально в `build/node/` (см. `references/tools.md`). Чего нет — записать как ограничение и понизить уверенность соответствующей фазы.
5. Завести `<OUT>/TASKS.md` (шаги фаз 1–9 под выбранную глубину) и дописать в `build/STATUS.md` через `--status` глубину, форматы, место папки, ветку.
6. Сказать владельцу одной строкой, где будет главный результат (`deliverables/index.html`, `REPORT.md`).
**Артефакты:** `build/env.json`, `build/git-status-before.txt`, `TASKS.md`, `build/STATUS.md`.
**Субагенты:** нет.
**Готово, когда:** `check_env.py` отработал, все «обязательные» инструменты есть или зафиксированы обходы; ветка создана (если нужна).

## Фаза 1. Понимание продукта по репозиторию (только чтение)

**Цель:** что за продукт, для кого, какую задачу решает, что уже есть, что неизвестно.
**Входы:** репозиторий, `env.json`, `run-config.product.known_facts`, `sources.owner_docs`.
**Шаги:**
1. `python3 <SKILL_DIR>/scripts/repo_scan.py <repo> <OUT>` → `data/repo-scan.json` + `research/repo-scan.md` (стек, точки входа, маршруты, функции с файлами, i18n, интеграции, качество, история git; секреты пропускаются и перечисляются в `secrets_skipped`).
2. Если `scope.issues` и есть `repo.remote` и `gh` — `python3 <SKILL_DIR>/scripts/issues_export.py <owner/repo> <OUT>` (только чтение Issues и PR) → `data/issues.json`, `research/issues-demand.md`. Классифицировать: запрос функции, жалоба, баг, вопрос; отметить, кто авторы (если почти все от одного человека или от QA — сигнал слабый, класс C).
3. Прочитать сам: README, docs, CHANGELOG, лицензию, манифесты, точки входа из скана, страницы цен/оплаты/входа, конфиги аналитики и фича-флагов. Не открывать `.env*`, ключи, дампы.
4. Написать `research/product-understanding.md` (1–2 страницы, ссылки `путь:строка`): JTBD, аудитория (известное/неизвестное), инвентарь функций (функция → файл → видна ли в UI), зрелость и темп разработки, стек, монетизация (что уже есть), распространение (домен, каналы), сильные стороны и пробелы, карта спроса из Issues, «что неизвестно и какие данные нужны владельцу».
**Скрипты:** `repo_scan.py`, `issues_export.py`.
**Субагенты:** quick/standard — нет. deep/exhaustive и большой монорепозиторий — 2–4 агента sonnet «прочитать папку X и вернуть инвентарь функций с `путь:строка`» (пути не пересекаются); при сотнях Issues — 1 агент sonnet на классификацию.
**Готово, когда:** у каждой функции инвентаря есть файл; раздел «Что неизвестно» заполнен; черновые вопросы владельцу записаны.

## Фаза 2. Запуск и изучение приложения

**Цель:** увидеть продукт глазами пользователя, снять факты: скриншоты, токены дизайна, пути, трения.
**Входы:** `product.url`, `product.local_run`/`run_command`, `repo-scan.json` (маршруты), `tools.browser`.
**Шаги:**
1. Запуск: команда из конфига → README/`Makefile`/`package.json`/Docker. Только тестовые данные и учётки из фикстур проекта; не трогать боевые базы. Не больше 3–4 попыток; дальше — публичный адрес; дальше — по коду с пониженной уверенностью (записать в STATUS).
2. Веб/PWA: `node <SKILL_DIR>/scripts/node/audit_site.mjs <URL> <OUT> --mobile [--pages /,/pricing] [--locales ru,en]` → `mockups/current/<slug>-<vp>.png` (десктоп 1440×900, мобайл 390×844), `mockups/tokens.css` (частотный анализ computed CSS), `data/site-audit.json` (meta/OG/hreflang/JSON-LD, тайминги, сторонние домены). Скрипт ничего не кликает и не отправляет формы. Затем пройти вручную главные пути: первый визит → посадочная → регистрация/вход (до формы, без отправки реальных данных) → первое действие → основной сценарий → возврат → оплата/донат (до платёжной формы, не дальше).
3. CLI/библиотека/API/SDK: `--help`, примеры, время до первого результата, понятность ошибок; вывод терминала сохранить текстом и отрендерить в PNG тем же браузером (`mockups/current/cli-*.png`).
4. Мобильное/десктоп/бот/игра: эмулятор или сборка, если есть; иначе ресурсы, описания в магазинах, скриншоты из репозитория — с пометкой «уверенность понижена».

6. Написать `research/ui-inventory.md`: карта экранов и состояний (пустые, ошибки, загрузка), карта путей, список трений и упущенных возможностей (каждое — со скриншотом и/или `файл:строка`), доступность (контраст, фокус, alt), SEO-теги, скорость, следы аналитики и оплаты. Эвристики без данных воронки помечать `[оценка: эвристика]`.
**Скрипты:** `audit_site.mjs`.
**Субагенты:** обычно нет (браузер — один, порядок важен). deep/exhaustive: 1 агент sonnet на UX/CRO-разбор по готовым скриншотам (входы — `mockups/current/`, выход — раздел в `build/parts/ux-review.md`, оркестратор вставляет в `ui-inventory.md`).
**Готово, когда:** есть хотя бы 1 реальный скриншот каждого ключевого экрана или записана причина отсутствия; `tokens.css` создан (или зафиксировано, почему нет — тогда нейтральная палитра); список трений ≥ 10 (standard).

## Фаза 3. Тип продукта и адаптация

**Цель:** выбрать акценты стратегии, категории и затравки реестра под тип продукта.
**Входы:** `product-understanding.md`, `ui-inventory.md`, `run-config.product.type`, `strategy.kind`.
**Шаги:**
1. Определить тип (или сочетание): `saas|consumer|devtool|oss|content|game|bot|mobile|desktop|other`. Если в конфиге `auto` — записать выбор и обоснование в `run-config.json → product.type` и `assumptions`.
2. Акценты по типу (таблица — ориентир; каналы и тактики проверяются поиском в фазе 4):

| Тип | Упор |
|---|---|
| `saas` (веб-сервис, B2B) | портрет клиента, позиционирование, воронка «посетитель → регистрация → активация → оплата», страницы цен и сравнения, интеграции, кейсы, SEO и GEO, партнёрские программы, онбординг, удержание команд |
| `consumer` | вирусные механики и шаринг, уведомления, удержание, отзывы, сообщества, короткие видео |
| `mobile` | ASO, отзывы в магазинах, push, офлайн, правила магазинов и их комиссии |
| `devtool` (библиотека, CLI, API) | документация и время до первого результата, примеры и шаблоны, интеграции и плагины, каталоги пакетов, README и звёзды, профильные форумы, статьи и конференции, лицензия и модель монетизации |
| `oss` | сообщество и вклад, хорошие первые задачи, дорожная карта, спонсорство и гранты, управление проектом, релизный ритм |
| `content` (контентный сайт, инструмент сообщества) | SEO и GEO, UGC, серии контента, партнёрства с авторами, рассылки, боты |
| `game` (игра или приложение вокруг игры) | сообщества, стримеры, сезонные события, моды и каталоги, правила платформ и IP правообладателя |
| `bot` (бот, расширение, плагин) | каталоги и магазины, правила платформ, вирусность через использование в чатах |
| `desktop` | дистрибуция (сайт, магазины, менеджеры пакетов), автообновление, лицензия/разовая покупка, офлайн |

   Записать в `product-understanding.md` раздел «Тип и акценты»: 5–7 главных рычагов, неприменимые категории реестра и их замена, особые риски (правила магазинов, IP, платёжные ограничения).
3. Отфильтровать `references/growth-library.md` по метке типа → список затравок для генераторов (`build/seeds.md`, по категориям). Слабые и неприменимые вычеркнуть сразу.
4. Для `strategy.kind` ≠ `growth` — выбрать замену разделов 6–9 стратегии (`references/strategy-outline.md`, таблица «Вид стратегии»).
5. Сформулировать 3–5 гипотез «главных ставок» (уточнятся после оценки).
**Субагенты:** нет (короткий синтез, делает оркестратор на opus).
**Готово, когда:** тип и акценты записаны; `build/seeds.md` есть; чекпоинт.

## Фаза 5. Реестр предложений

**Цель:** `strategy.proposals_min` (± по глубине) качественных предложений с доказательствами.
**Входы:** всё из фаз 1–4, `build/seeds.md`, `references/methodology-anchors.md`.
**Шаги:**
1. Разбить категории на группы `G1…Gn` (пример для standard: G1 product, G2 product+platform, G3 acquisition, G4 conversion+retention, G5 monetization+analytics, G6 partnerships+localization+new_lines). Квота кандидатов группы = доля категории × число кандидатов из таблицы глубины.
2. Раздать `registry-generator.md` (sonnet при standard; opus для групп product и monetization на deep/exhaustive) → `data/proposals-draft-<G>.json`.
3. Принять выдачу: однострочник обязательных полей из брифа генератора по каждому черновику (`check_registry.py` проверяет только итоговый `proposals.json`), глазами — 5 случайных предложений на группу (доказательства реальны? шаги конкретны?).
4. `python3 <SKILL_DIR>/scripts/merge_proposals.py <OUT> --dry-run` — посмотреть найденные дубли (порог Жаккара `--threshold`, по названию `--title-threshold`); семантические дубли, которые скрипт не поймал, оркестратор сливает вручную в черновиках (лучший текст + все доказательства; запись в STATUS), затем `merge_proposals.py <OUT>` → `data/proposals.json` (`P001…`, `merged_from`).
5. `python3 <SKILL_DIR>/scripts/check_registry.py <OUT>`: обязательные поля, минимумы категорий, доля A+B ≥ 60 %, формат URL, длина цитат. Не прошло → дозаказать генератору недостающее (новый бриф с указанием дыр), не ослаблять проверку.
6. `python3 <SKILL_DIR>/scripts/check_links.py <OUT>` (проверяет `sources.json`, `evidence`, `steps.doc_url`, `competitors.json`; `--strict` — код 1 при мёртвых) — мёртвые ссылки заменить или понизить класс.
**Готово, когда:** `check_registry.py` зелёный; число предложений в пределах глубины; чекпоинт с распределением по категориям и классам.

## Фаза 6. Оценка

**Цель:** ранги, приоритеты, чувствительность, модель экономики.
**Входы:** `data/proposals.json`, `references/scoring.md`, `references/methodology-anchors.md`.
**Шаги:**
