# Правила безопасности

Самый важный файл скила. **Полный текст раздела «Блок правил для исполнителей» (ниже) дословно вставляется в задание каждого субагента, плагина и агента плагина** — вместе с разобранными правилами пользователя из run-config. `<SKILL_DIR>` подставляется фактическим путём из `run-config.yaml → skill_dir` (`scripts/skill_dir.py`), а не путём рабочей копии или «как было в прошлый раз».

**Главный принцип: сбой защиты — не разрешение (fail closed).** Если guard не отвечает решением 0/2/3 — действие не выполняется (§3 п. 0).

## 1. Базовые запреты (всегда, отключить нельзя)

| # | Запрет | Реализация |
|---|--------|------------|
| B1 | Не совершать покупки, оплату, подписки, донаты; не вводить платёжные данные | `url_guard` action: категория `purchase` → deny; навигация на платёжные шлюзы и `/checkout`, `/payment`, `/subscribe`, `/donate` → deny |
| B2 | Не подтверждать привязку внешних аккаунтов, OAuth/OpenID (Steam, Google, Discord, Apple, VK, Яндекс…). Не нажимать «Да», «Разрешить», «Войти через…», «Sign in through Steam» | категория `oauth` → deny; «Да/OK/Allow» в диалоге с контекстом OAuth/оплаты → deny (`base:dialog-confirm`); хосты входа — `base:nav-host` |
| B3 | Не удалять данные, аккаунты, сохранения; не менять настройки боевого аккаунта | `account-destructive` → deny; `destructive`, `settings` → confirm; `/logout`, `/account/delete` → deny |
| B4 | Не отправлять формы, уходящие реальным людям (обратная связь, сообщения, жалобы, комментарии, приглашения), без явного разрешения на **каждую** отправку | `send-to-people` → confirm (если контекст — обратная связь/сообщение/жалоба/комментарий/чат) |
| B5 | Не принимать соглашения от имени пользователя, не обходить капчу и защиту | `agreement` → deny; капча → стоп, вопрос пользователю |
| B6 | Никаких нагрузочных тестов, перебора, сканеров уязвимостей, инъекций. Безопасность — только пассивно | плагины с активными атаками в бан-листе (`check_env` → `banned`); ввод — только безобидные граничные значения |
| B7 | Паузы между действиями, разумный темп | `parallel.throttle_ms` (по умолчанию 1500 мс) между действиями в браузере; node-скрипты имеют `--throttle` |
| B8 | Маскировать в отчётах и issues секреты, токены, e-mail, cookies, персональные данные | правило маскирования (п. 5) перед записью находки |
| B9 | Не выходить на внешние страницы: навигация только в `allowed_domains` | `url_guard nav` перед каждым переходом; внешние вкладки закрываются |
| B10 | Учётные данные — только из переменных окружения; никогда не печатать их, не писать в логи, отчёты, issues, скриншоты | вводить через `browser_type` значение, прочитанное из env самим исполнителем; скриншоты форм входа не делать |

`url_guard.py` — помощник, а не замена суждению: если элемент **по смыслу** попадает под запрет (кнопка-иконка без текста «корзина», «💳»), это запрет, даже если guard вернул allow.

## 2. Пользовательские запреты

Пользователь пишет свободным текстом; скил разбирает его в правила `rules` run-config и **показывает на подтверждение** таблицей «фраза → правило».

| Поле | Что значит |
|------|-----------|
| `forbidden_domains` | хосты/маски (`*.example.net`): ни навигации, ни загрузки ресурсов |
| `allowed_domains` (в `site`) | единственные хосты для навигации |
| `forbidden_url_patterns` | регэкспы по полному URL: туда не переходить |
| `forbidden_actions` | `texts` (на всех языках сайта), `roles`, `selectors`, `context`, `url_pattern` — действие не выполнять |
| `require_confirmation_actions` | те же поля — выполнять только после «да» пользователя в моменте |
| `preapproved_actions` | те же поля — заранее одобренные пользователем действия уровня confirm (например, «можно удалять собственные тестовые записи»). Снимают только confirm; базовые и пользовательские **запреты (deny) не снимают никогда** |

### Примеры разбора
| Фраза | Правило |
|-------|---------|
| «не выходить за домен» | `allowed_domains: [<host>]` без поддоменов (уточнить: поддомены можно?) |
| «не нажимать да при подключении steam» | `forbidden_actions: {id: U1, texts: [Да, Yes, OK, Allow, Разрешить, Sign in], context: steam}` + `forbidden_domains: [steamcommunity.com, *.steampowered.com]` |
| «не трогать раздел профиля» | `forbidden_url_patterns: ["/(profile|account|me|settings)(/|$)"]` + `forbidden_actions: {texts: [Профиль, Profile, Аккаунт, Account], roles: [link, button]}` — показать пользователю найденные на разведке URL раздела |
| «ничего не покупать» | уже покрыто B1; добавить тексты на языках сайта, найденные на разведке («В корзину», «Buy now», «Купить за 99 ₽») |
| «не отправлять форму обратной связи» | `forbidden_actions: {texts: [Отправить, Send, Submit], context: "обратн|feedback|contact"}` + `url_pattern` страницы формы. Заполнять поля для проверки валидации можно, отправлять — нет |
| «спрашивай перед удалением» | `require_confirmation_actions: {texts: [Удалить, Delete, Remove]}` |
| «удалять свои тестовые записи можно» | `preapproved_actions: {texts: [×, Delete, Удалить], context: "<контекст списка>"}` — только для данных, созданных прогоном |

Правило неоднозначно → вопрос с вариантами (`AskUserQuestion`), а не догадка.

## 3. Применение

0. **Fail closed — сбой защиты не разрешение.** Решение guard — только по коду выхода 0 / 2 / 3. **Код 4** («guard недоступен»: нет `--config` или файла, битый YAML, неверный регэксп в правилах, неверные аргументы, внутренняя ошибка), **любой другой код**, «No such file», «command not found», пустой вывод, таймаут — это **СТОП**: переход и действие не выполнять, дальше не продолжать, сообщить оркестратору/пользователю «guard недоступен: <вывод>». В node-скриптах то же делает `guard.js` (`GuardUnavailableError`, код 4): ничего не нажимается и никуда не переходит, скрипт завершается с кодом 4.
1. **Перед каждым переходом** (`browser_navigate`, клик по ссылке, `window.open`): `python3 <SKILL_DIR>/scripts/url_guard.py nav <URL> --config <RUN_DIR>/run-config.yaml`. Код 3 (deny) → не переходить; если это ссылка на внешний сайт — записать в отчёт «ведёт на X — не проверялось». Код 4 или другой → п. 0.
2. **Перед каждым кликом, отправкой формы, подтверждением диалога**: `url_guard.py action --text "<видимый текст>" --name "<aria-label/title/alt>" --role <role> --url <текущий URL> --context "<заголовок диалога/формы, ближайший текст>" --config <RUN_DIR>/run-config.yaml`. Для кнопок-иконок (×, 🗑, ✕) **обязательно** передавать `--name`: по одному символу guard видит лишь «иконку удаления».
   - 0 allow → выполнять; 2 confirm → спросить пользователя (одно действие — одно подтверждение, если не дано общее разрешение на класс действий в этом прогоне); 3 deny → не выполнять; 4 или другое → п. 0 (стоп).
3. **Нативные диалоги** (`confirm`, `beforeunload`, `prompt`): по умолчанию отклонять (`browser_handle_dialog accept=false`). Принять можно только если текст диалога прошёл `action` с allow.
4. **Новые вкладки**: после действия проверить `browser_tabs list`. Вкладка на внешний домен — закрыть сразу, зафиксировать URL в отчёте.
5. **Редиректы**: после навигации сверить фактический URL (`location.href`) через `url_guard nav`. Оказались вне allowlist — вернуться назад, ничего не нажимать, записать находку/заметку.
6. **Ресурсы**: загрузка с CDN, тайлов, API, шрифтов разрешена; блокируются только `forbidden_domains` и базовые `blocked_origins`. В node-скриптах это делает `guardContext` (rules.json из `url_guard.py export`).
7. **`--blocked-origins` Playwright MCP**: используется, если пользователь подключил MCP с этим флагом (строку даёт `url_guard.py blocked-origins`). `--allowed-origins` не используем — ломает CDN и тайлы, а границей безопасности не является.
8. **Запрещённое действие** не выполняется; в отчёт: «не проверено: запрет <id правила> (<источник>)». Если без него не проверить важную функцию — спросить пользователя (варианты: пропустить / разрешить один раз / показать, как проверить вручную).
9. **Плагины и их агенты**: используются, только если их действия идут через нашего исполнителя (скил-методика) или агент принимает блок правил и выполняет `url_guard` перед действиями. Агент, который сам кликает без проверки или в описании имеет активные атаки, — в этом направлении не используется (`banned` в check_env: `adversarial-breaker`, opentest `perf-test`).
10. **Логин**: тестовый аккаунт — данные из env (`auth.username_env`, `auth.password_env`); ручной вход — пользователь входит сам в открытом окне (`browser_navigate` на страницу входа, затем пауза и вопрос «вошёл?»). Скил не вводит чужие пароли, не сохраняет cookies сессии в отчёты.

11. **Замок навигации** (`scripts/nav_lock.js`): если охват — «только эти страницы» (`scope.type: url-list` / `current-screen`) или пользователь запретил любые переходы, сразу после открытия страницы передать файл в `browser_run_code_unsafe`, заменив `__ALLOWED_RE__` на регэксп разрешённых URL. Замок обрывает навигацию документа и блокирует `pushState`/`replaceState`/`window.open` SPA-роутеров — guard не видит, что кнопка без `href` сменит адрес. Попытки (`window.__qaNavAttempts`) переносятся в отчёт в раздел «Сработавшие запреты».
12. **Кнопки провайдеров входа** («Google», «Яндекс», «VK», «Steam»…) рядом с фразой «войдите через / sign in with» — всегда передавать в `--context` текст этой фразы: guard запрещает их как OAuth (`base:action:oauth-provider`).
13. **Только чтение** (`url_guard.py nav <URL> --read-only --log <RUN_DIR>/logs/read-only.jsonl`): страницу покупки, доната, подписки (`/checkout`, `/payment`, `/pay/`, `/billing`, `/subscribe`, `/donate`) и URL из `rules.read_only_urls` (например, страницы входа и регистрации, если пользователь разрешил их **читать**) можно открыть, чтобы прочитать цену, тексты согласий и ссылки на документы. На такой странице **ничего не нажимать, не заполнять и не отправлять**; в журнал пишется «прочитано без действий». Не снимается никогда: OAuth/OpenID, выход, удаление аккаунта, платёжные шлюзы и хосты входа, чужие хосты, `forbidden_domains`. В node-скриптах — `guardContext(ctx, rules, { readOnly: true })` + `guardedPage(page, rules, { readOnly: true })`: переход разрешён, все действия — deny `read-only`, запросы кроме GET/HEAD/OPTIONS обрываются. Вместо `curl` мимо guard — только так.

## 5. Маскирование

Перед записью в findings.json, отчёт, черновик, issue:
- e-mail → `a***@d***.tld`; телефоны → последние 2 цифры;
- токены, ключи, JWT, session id, cookies → первые 4 символа + `…` + длина: `ghp_…(40)` (тип ключа виден, значение — нет);
- URL с `token=`, `key=`, `session=`, `code=`, `state=` — значения параметров заменить на `***`;
- имена/логины реальных пользователей, видимые на страницах, → `<пользователь>`;
- скриншоты с персональными данными — не публиковать или замазать (`browser_evaluate`: временно заменить текст узлов перед снимком).

## 6a. Правовые и финансовые утверждения
Утверждения о нормах права, санкциях, штрафах, налогах и других последствиях с высокой ценой ошибки:
- в находке — наблюдаемый факт; нормы — только «возможно применимо» в `legal.norms` (с юрисдикцией), без вывода «нарушает закон»;
- **вторая проверка другим исполнителем** (не тем, кто нашёл) по первоисточнику — `recheck.py legal <RUN_DIR> --id F-NNN --by "…" --result confirmed|corrected|rejected`;
- в тексте issue и отчёта — пометка «требуется проверка юристом» (`render_draft.py` ставит её сам);
- без второй проверки — не публиковать как факт (`recheck.py gate`, сводная таблица). Подробно — `checklists/legal-ui.md`.

## 6. Серьёзная утечка
Найден действующий ключ/токен, пароль или персональные данные других пользователей:
- находка получает severity `critical` и флаг `evidence.sensitive: true`;
- **публикация такой находки в публичные репозитории останавливается** — только вопрос пользователю (варианты: «только в приватный репозиторий-копию» / «только локальный отчёт» / «сообщить владельцу сайта другим путём»);
- в черновиках и отчёте — только маскированное значение и место (URL скрипта, строка), без скриншота с самим значением.
