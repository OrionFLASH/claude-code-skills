# После аудита: доработка, независимое ревью, закрытие

Скил находит и описывает проблемы; исправляют их разработчики или агенты-исполнители. Этот справочник — как довести цикл «аудит → issues → доработка → закрытие» до проверяемого результата. Шаги, которые делает сам скил, отмечены командами; остальное — порядок работы оркестратора.

## 1. Из находок — issues
- Одна первопричина — один issue: `render_draft.py group findings.json --map groups.yaml --run-dir <RUN_DIR>` (`repo-sync.md` → «Группы по первопричине»). Проявления на разных экранах, устройствах и в разных потоках — таблицей в одном issue, по маркеру на каждую находку.
- В каждом issue — блок **«Как проверить»** (из `verify` и `repro` находки): условие «до исправления — да, после — нет» или сценарий; по нему закрытие проверяемо.
- Заготовка регрессионного теста — `e2e_stub.py` (Playwright, из `steps[]` и `repro`); исполнитель доработки доводит её, а не пишет тест с нуля.
- **Запуск заготовки скилом** — `node/e2e_run.js` (раздел ниже): до передачи разработчику убедиться, что заготовка падает **на проверке дефекта**, а после исправления — проходит три раза подряд.

### Заготовка e2e: запуск (`node/e2e_run.js`)
```bash
python3 <SKILL_DIR>/scripts/e2e_stub.py <RUN_DIR>/findings.json --id F-001 --out <RUN_DIR>/drafts/e2e/F-001.spec.ts
# до исправления: тест должен упасть на проверке дефекта
node <SKILL_DIR>/scripts/node/e2e_run.js <RUN_DIR>/drafts/e2e/F-001.spec.ts --rules <RUN_DIR>/rules.json \
  --app-url file:///…/app/ --expect fail --log <RUN_DIR>/logs/blocked.jsonl --out <RUN_DIR>/raw/e2e-F-001.json
# после исправления: три прогона подряд (по умолчанию для --expect pass)
node <SKILL_DIR>/scripts/node/e2e_run.js <RUN_DIR>/drafts/e2e/F-001.spec.ts --rules <RUN_DIR>/rules.json \
  --base-url https://stage.example.com --expect pass
```
- Это настоящий Playwright Test из пакета `playwright` скила — ставить `@playwright/test` не нужно (он лишь переэкспортирует `playwright/test`). Заготовки копируются во временную папку (рядом нет `node_modules` проекта), импорт `@playwright/test` направляется (`NODE_PATH`) на обёртку `scripts/node/e2e/shim`, которая добавляет к каждому контексту теста **guard прогона** — и больше ничего не меняет. Переход вне правил, `file://` вне `local_roots`, запрещённые пути обрываются и пишутся в `--log`; адреса `page.goto(new URL(…, APP_URL|BASE_URL))` проверяются ещё до запуска (код 3). Без `--rules` — код 4.
- `--expect fail` засчитывается, только если тест упал на `expect(…)` заготовки; падение на переходе, таймауте или сломанном селекторе — «не как ожидалось» (заготовку надо чинить). `--expect pass` — все повторы (`--repeat-each`, по умолчанию 3) прошли; `test.fixme` (нет `repro`) проходом не считается.
- Окно — как у всех скриптов: `--headed` / `--headless`, `--slowmo`, `browser.headed` прогона, `SITE_QA_HEADLESS`. Браузер — по устройству заготовки (`devices["iPad (gen 7)"]` → WebKit), `--browser` — принудительно.
- Ограничения: поддержаны заготовки `e2e_stub.py` — TypeScript (`.spec.ts`) и CommonJS (`.spec.js`); ESM-файлы (`.mjs`) обёртка не поддерживает (`NODE_PATH` не действует на `import` в ESM). В проекте разработчика тест запускается его собственным `npx playwright test` — без guard скила.
- Сводный issue: что проверено, что нет (`thread_coverage.py summary`, вторая волна — `thread_coverage.py again`), варианты данных и стенды, которые не входили в охват.

## 2. Доработка (исполнитель)
1. Тест, **падающий до правки** (заготовка `e2e_stub.py` или свой), → правка → тест зелёный.
2. Проверка на реальных данных и на **каждом варианте данных и стенде** из `run-config.yaml → variants` (поле, которого нет на другом стенде, — частая причина регрессий, которые не видит ни аудит, ни исполнитель).
3. Новый e2e — **три прогона подряд** до сдачи (`npx playwright test <файл> --repeat-each=3`; в прогоне скила — `e2e_run.js … --expect pass`): гонки анимаций и таймеров ловятся только так. Ждать состояния (`toBeVisible`, `toHaveCSS`, `waitForFunction`), а не фиксированных пауз.
4. Документация пользователя («Что нового», справка) — отдельным файлом-фрагментом на задачу (например, `whatsnew/<номер>.md`), а не дописыванием в конец общего файла: параллельные доработки иначе конфликтуют в одном месте при слиянии.
5. Коммиты в своей ветке; слияние и закрытие issues — не исполнителя.

## 3. Слияние и **независимое ревью диффа** (обязательно)
После слияния веток доработки: полный прогон тестов на **слитом** дереве (нестабильные тесты проявляются здесь), затем ревью **отдельным агентом только на чтение** — не тем, кто правил, и не оркестратором, который сливал. На опыте такое ревью нашло 8 дефектов (1 high), которых не видели ни аудит, ни исполнители.

Задание ревьюеру (заполнить и передать целиком):
```text
Ты — независимый ревьюер доработок по issues <список>. Только чтение: ничего не правь, не коммить, не публикуй.
Дифф: <git diff main...<ветка> или список коммитов>. Issues и их блоки «Как проверить»: <ссылки или текст>.
Варианты данных и стенды: <variants из run-config>. Тесты: <команда полного прогона>.
Проверь по каждому issue:
1. Исправлена причина, а не симптом; все проявления группы (таблица в issue) закрыты.
2. Правка не ломает другие варианты данных и стенды (поля, форматы, пустые значения, локали).
3. Регрессионный тест есть, падал бы до правки, проходит три раза подряд; нет фиксированных пауз вместо ожиданий.
4. Граничные значения, пустые и очень длинные данные, повторное действие, отмена, «Назад».
5. Нет посторонних изменений, отладочного кода, секретов; документация пользователя обновлена.
Ответ: для каждого issue — «замечаний нет» или замечания (severity, файл:строка, как воспроизвести).
Новые дефекты — отдельным списком: их заведут новыми issues.
```
Замечания ревьюера → новые issues (второй заход) или возврат исполнителю; без ревью issue не закрывается.

## 4. Перепроверка и закрытие
- Перепроверка заявленных исправлений скилом — режим «Перепроверка исправлений» (`claims.md`): `claims.py extract` → `plan` → проверка → `claims.py set`; по каждому — FIXED-OK / FIXED-INSUFFICIENT / REGRESSION / NOT-CHECKED.
- Закрывать комментарием из трёх строк:
  ```text
  Что изменено: <кратко, ссылка на коммит/PR>
  Чем проверено: <тест (3 прогона), «Как проверить» из issue, варианты данных/стенды, ревью — «замечаний нет»>
  Осталось: <ничего | новые issues #…>
  ```
- Вопрос к владельцу, на который нет ответа, — issue остаётся открытым с вопросом, не закрывается «по умолчанию».
