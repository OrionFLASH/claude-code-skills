# Опрос на входе

Цель — получить полный `run-config.yaml` (схема: `templates/run-config.example.yaml`).

## Подтверждение намерения
Нужно, только если скил подхвачен **по смыслу запроса**, а не вызван явно. Явный вызов — команда `/site-qa-audit` (в ходе есть `<command-name>/site-qa-audit</command-name>`): подтверждение пропускается.

Первое действие скила — до `check_env`, создания папок и открытия браузера — один `AskUserQuestion`:
- вопрос: «Похоже, вы хотите протестировать <объект>. Запустить QA-аудит?»; в тексте пересказать понятое из запроса: объект (URL, раздел, «интерфейс приложения»), направления (вёрстка, доступность, скорость…), устройства, запреты — **только названное**, без догадок;
- варианты: «Да, запустить аудит (Recommended)» / «Да, но сначала уточнить задачу» / «Нет, это другое».

| Ответ | Что дальше |
|-------|------------|
| «Да, запустить аудит» | обычный порядок работы; понятое из запроса не переспрашивать |
| «Да, но сначала уточнить задачу» | опрос ниже, начиная с вопроса 2 «Что именно тестируем» |
| «Нет, это другое» | скил прекращает работу: **ничего не создавать** (ни `qa-runs/`, ни файлов, ни `check_env --json`), не открывать браузер; ответить на исходный запрос как обычно, без скила |
| нет ответа / непонятно | не начинать; один уточняющий вопрос |

Пример: «Похоже, вы хотите протестировать https://shop.example.com — вёрстку и адаптив на телефоне, ничего не покупая. Запустить QA-аудит?»

## Правила опроса
- Спрашивать инструментом вопросов с вариантами (`AskUserQuestion`), **по 1–3 вопроса за раз**, рекомендуемый вариант — первым с пометкой «(Recommended)».
- **Уже переданное в запросе не переспрашивать.** Сначала разобрать запрос пользователя: URL, глубина, направления, репозитории, запреты, режим — всё, что можно извлечь. Черновик конфига из свободного текста — `scripts/intake.py from-text` (ниже); он не заменяет подтверждение.
- Ответ «по умолчанию» / «как обычно» → брать значения по умолчанию из таблицы ниже.
- У `AskUserQuestion` до 4 вариантов на вопрос и до 4 вопросов за вызов. Длинный список (направления, запреты, источники) — несколькими вопросами в одном вызове, по смысловым группам. Вариант «Свой вариант (опишу)» — это встроенный свободный ввод инструмента («Other»), отдельной кнопкой его не добавлять.
- Порядок порций (что уже есть в запросе — пропустить): ① URL, что тестируем, что считать успехом → ② вход, устройства, глубина → ③ запреты, куда не переходить → ④ откуда узнать о сайте → ⑤ репозитории → ⑥ куда записать итоги, потоки, режим.
- Секреты не спрашивать в чате: только **имена** переменных окружения. Если пользователь вставил пароль/токен в чат — не повторять его, предложить вынести в env.

## Папка прогона
`<RUN_DIR>` = `<OUTPUT_ROOT>/qa-runs/<YYYY-MM-DD>-<host>/`. Если за сегодня папка есть — суффикс `-2`, `-3`.

`<OUTPUT_ROOT>` выбирается так (первое подходящее):
1. Путь, явно названный в запросе («сохрани в …») → без вопроса.
2. `output_dir` из повторяемого `run-config.yaml`.
3. Переменная окружения **`SITE_QA_OUTPUT_DIR`** (задаётся пользователем один раз, например в `env` файла `~/.claude/settings.json`) → без вопроса, путь показывается в сводке.
4. Иначе — **`<cwd>`**, папка, из которой запущен Claude Code: результаты в `<cwd>/qa-runs/` (внутри проекта, без вопроса; путь показывается в сводке; в конце прогона — вопрос про `.gitignore`, ниже). Если `<cwd>` — домашняя папка (`~`) или репозиторий скилов, писать туда нельзя: тогда **вопрос** «Куда сохранять результаты?» (варианты: «Указать путь» / «Отмена»; подсказка: задать `SITE_QA_OUTPUT_DIR`).

**Всё в одном месте.** Файлы прогона (в том числе разовые перепроверки, скриншоты, вывод скриптов проекта) создаются только в `<RUN_DIR>`. Папки вроде `findings/`, `screenshots/` в корне проекта не создавать; прошлые наработки там не переносить без запроса.

Никогда не писать результаты в репозиторий скилов. Выбранный путь (абсолютный) записывается в `run-config.yaml → output_dir` и показывается в сводке перед «старт».
```
run-config.yaml  env.json  rules.json  findings.json  matches.json  report.md  summary.md  journal.md
claims.json  claims-plan.md  rechecks.json (перепроверка заявлений)  side_effects.md (если были)
screenshots/  logs/  drafts/  raw/ (вывод node-скриптов и плагинов)
```
Общие для прогонов: кэш issues `<OUTPUT_ROOT>/qa-runs/.cache/issues/` (передавать в `fetch_issues.py --cache`) и память о сайте `<OUTPUT_ROOT>/qa-runs/.site-context/<host>/` (`run-files.md`).

**Повтор прогона:** если в `<OUTPUT_ROOT>/qa-runs/` есть прошлые `run-config.yaml` для того же хоста — первым вопросом предложить: «Повторить конфиг от <дата>» / «Повторить, но изменить…» / «Новый опрос».

## Память о сайте
Первым делом, как только известен хост (из URL запроса), — файл `<OUTPUT_ROOT>/qa-runs/.site-context/<host>/context.md` (`<host>` — имя хоста в нижнем регистре, без `www.` и порта). Формат и правила хранения — `run-files.md` → «Память о сайте».
- **Есть**: прочитать, показать резюме в 3–6 строк (назначение, роли, основные сценарии, дата изучения и источники) и спросить вместе с «Повтором прогона» (если он есть), одним вызовом: «Использовать как есть (Recommended)» / «Обновить» / «Изучить заново» → `context.reuse: as-is | update | relearn`.
  - `as-is` — вопросы 11–11a не задавать; контекст учитывать в плане и передавать исполнителям;
  - `update` — вопрос 11 с прошлыми источниками из `sources.json` как отмеченными; изучать только новое и изменившееся;
  - `relearn` — полный вопрос 11; прошлая версия сохраняется рядом как `context.prev.md`.
- **Нет**: `context.reuse: new`, вопросы 11–11a по таблице.

### 12. Репозиторий (на каждый)
1. URL (`https://github.com/owner/repo` или `owner/repo`).
2. Роли (мультивыбор):
   - `check` — только сверка;
   - `write-new` — сверка и запись **новых** находок по **их** шаблону;
   - `copies` — подробные копии **всех** находок **своим** шаблоном (`templates/issue-detailed.md`);
   - `comment` — комментарии к существующим issues (FIXED-INSUFFICIENT, REGRESSION).
3. Стиль: кратко / подробно.
4. Метки: только существующие / можно создавать свои / писать строкой в теле.
5. Подтверждение перед публикацией: включено (по умолчанию) / выключено (предлагать только для своего репозитория — где у пользователя admin).
6. Скриншоты: коммитить в этот репозиторий (`runs/<дата>/`, нужен `push`) → `commit` / загрузить через веб-форму GitHub в браузере пользователя (чужой или приватный репозиторий) → `web-upload` (`web-upload.md`) / не класть → `none`.
7. Раскрытие (для чужого репозитория и копии): «Подпись и маркер скила (Recommended для своего)» / «Без упоминания скила и Claude» → `disclosure: full|none`; маркер `skill|neutral|none`.
8. Ссылки на другие репозитории: «Да» / «Не связывать репозитории» → `cross_links: true|false`.
9. Недоработка исправления в **закрытом** issue: «Комментарий в нём (Recommended)» / «Новый issue» / «Пропустить, только отчёт» → `closed_claims: comment|new|skip`.
10. Шкала серьёзности репозитория (из формы и документов, `read_templates.py fetch`): показать соответствие и записать `severity_map`.

Сразу после ввода — `fetch_issues.py meta owner/repo` и сверка прав с ролями по таблице `repo-sync.md` §1 (issues включены; метки — `triage`; скриншоты — `push`). Если прав не хватает — сообщить и предложить: понизить роль до `check` / указать другой репозиторий / оставить черновики в `drafts/`.

### 13. Какие действия делать нельзя: чек-лист (мультивыбор, три вопроса одним вызовом)
Базовые запреты (`safety-rules.md` §1) действуют всегда — пункты ниже их уточняют текстами кнопок сайта или ужесточают. Отмеченные пункты → правила `rules` на подтверждение (таблица «пункт → правило»).

| Группа | Пункт | Правило |
|--------|-------|---------|
| Деньги и аккаунт | Покупки и оплата | уже B1; добавить тексты кнопок сайта, найденные на разведке («В корзину», «Купить за …») |
| | Регистрация новых аккаунтов | `forbidden_actions: {texts: [Зарегистрироваться, Sign up, Register, Создать аккаунт]}` + `forbidden_url_patterns: ["/(signup\|register\|registration)(/\|$)"]`; поля формы заполнять для проверки валидации можно, отправлять — нет |
| | Смена настроек аккаунта (язык, регион, валюта, тема, профиль, пароль) | `forbidden_actions: {texts: [Сохранить, Save, Применить, Apply], url_pattern: "/(settings\|account\|profile)"}` (URL раздела — с разведки) + переключатели языка/валюты — `texts` на языках сайта |
| | Не трогать раздел профиля/аккаунта | `forbidden_url_patterns: ["/(profile\|account\|me\|settings)(/\|$)"]` (`safety-rules.md` §2) |
| Формы и данные | Отправка любых форм (не только людям) | `forbidden_actions: {texts: [Отправить, Send, Submit, Оставить заявку], roles: [button]}`; заполнять поля можно, отправлять — нет |
| | Удаление чего-либо (даже своих тестовых записей) | `forbidden_actions: {texts: [Удалить, Delete, Remove, ×]}` — снимает возможность `preapproved_actions` |
| | Спрашивать перед любым удалением | `require_confirmation_actions: {texts: [Удалить, Delete, Remove]}` |
| | Не загружать файлы | `forbidden_actions: {texts: [Загрузить, Upload, Выбрать файл, Choose file]}` (guard.js проверяет и `setInputFiles`) |
| Выход за пределы | Подписка на рассылки и уведомления | `forbidden_actions: {texts: [Подписаться, Subscribe, Получать новости, Включить уведомления]}`; разрешение браузера на уведомления — отклонять |
| | Переходы по внешним ссылкам | уже B9 (навигация только в `allowed_domains`); внешние ссылки только перечислить в отчёте (`links.js`), не открывать |
| | Не выходить за домен (строго один хост) | `allowed_domains: [<host>]` без `*.<host>` |
| | Не нажимать рекламу и партнёрские ссылки | внешние — уже B9; `forbidden_domains` рекламных и партнёрских сетей (с разведки) + `forbidden_actions: {texts: [Реклама, Sponsored, Партнёр]}` для промо-блоков сайта |

Вход через внешние аккаунты (Steam, Google, Discord…) уже запрещён базовым B2 — конкретных провайдеров можно указать свободным текстом.
Как срабатывает правило (`url_guard.py`): `texts` — точный текст или подстрока длиннее 3 символов; `url_pattern` — регэксп по URL; `context` — **подстрока** текста диалога/формы (не регэксп: для нескольких слов — несколько правил); правило без `texts`, `selectors` и `url_pattern` не срабатывает.

Свободный текст разбирается по `safety-rules.md` §2 → таблица «фраза → правило» на подтверждение.

Если сценарии требуют создавать и удалять тестовые данные (списки, корзины-черновики, заметки), спросить: «Разрешить заранее удаление записей, созданных самим прогоном?» → `preapproved_actions`. Иначе каждое удаление — отдельный вопрос.

### Побочные эффекты (спрашивать, если на сайте есть загрузка файлов, публикация, рейтинги, рассылки, привязки)
Вопрос: «Какие действия на сайте имеют последствия за пределами теста (публичный рейтинг, рассылка, привязка аккаунта, необратимая загрузка, публичная запись)? Какая защита нужна перед ними или сразу после?» Варианты: «Таких нет» / «Есть — опишу» / «Не знаю, найти на разведке и показать».
- Ответ → `side_effects` (действие, цель, последствие, что остаётся: локальные копии, скрытые записи) и `invariants` («после загрузки за N мс должен появиться и быть отмечен флажок X, иначе остановиться») — формат и команды в `side-effects.md`.
- Название защитного элемента записать регэкспом, устойчивым к переименованию («Чуж(ой|ое)»), и точным текстом в `vocabulary`; при повторе прогона — передать `vocabulary.json` прошлого прогона в `invariants.js preflight --prev-vocab`.
- Если пользователь не может описать защиту — действие с эффектом не выполнять (`forbidden_actions`), а в отчёт: «не проверено: побочный эффект без защиты».

Вход `manual-cdp` («я уже вошёл в своём Chrome»): спросить адрес CDP (по умолчанию `http://127.0.0.1:9222`, Chrome запущен с `--remote-debugging-port=9222`); в этом режиме cookies и localStorage не очищаются — `devices-auth.md`.

### 16. Параллельные потоки (1–4)
Скил может проверять одновременно несколько **независимых** направлений, групп страниц или гипотез — до 4 потоков (`parallel.max_workers`, по умолчанию 2). Предлагать 3–4, только если независимых задач не меньше числа потоков, есть `playwright-cli`, вход гостевой или у каждого потока свой тестовый аккаунт и нет действий с побочными эффектами (`parallelism.md` → «Сколько потоков»). Общая сессия входа (`manual`, `manual-cdp`) — один браузерный поток без вопроса. Ответ больше 4 — записать 4 и сказать об этом.

### 18. Куда записать итоги (`report_destinations`)
Локальная папка `<RUN_DIR>` есть всегда; вопрос — о **дополнительных** местах. Что делает скил в шаге «Итоги» (SKILL.md, шаг 11):

| Ответ | `type` | Что делает скил |
|-------|--------|-----------------|
| «Только локальная папка (Recommended)» | `local` | ничего дополнительно: `report.md` и `summary.md` в `<RUN_DIR>` |
| «Другая папка на диске (путь)» | `folder` + `path` (абсолютный) | копирует `report.md` и `summary.md` в `<path>/<YYYY-MM-DD>-<host>/` (папку создаёт; существующие файлы с теми же именами не перезаписывает без вопроса) |
| «GitHub issues в репозитории» | `github` + `repo` | сценарий репозиториев (`repo-sync.md` §4–5): репозиторий добавляется в `repos[]` (если его там нет — вопросы «Репозиторий», п. 12, роль по ответу; права — `fetch_issues.py meta`), итоговый issue со сводкой `summary.md` и ссылками на созданные issues; подтверждение по сводной таблице; в dry-run — черновик в `drafts/` |
| «Страница-артефакт Claude (Artifact)» | `artifact` | если в сессии есть инструмент `Artifact` — страница из `report.md` (приватная по умолчанию; без находок с `evidence.sensitive`, секретов и персональных данных), ссылка — в `report.md`; инструмента нет — пропуск, в `report.md`: «Artifact: не опубликовано — инструмент недоступен в сессии» |
| свободный ввод | `custom` + `note` | выполнить описанное только после отдельного подтверждения в конце прогона; невыполнимо — пропуск с причиной в `report.md` |

Пути и ссылки результата — раздел «Куда записаны итоги» в конце `report.md` (`run-files.md`).

## В конце прогона: qa-runs/ и git
После отчёта (SKILL.md, шаг 11) — `python3 <SKILL_DIR>/scripts/gitignore_helper.py check <OUTPUT_ROOT>`:
- код 0 — `<OUTPUT_ROOT>` не в git-репозитории, `qa-runs/` уже игнорируется или пользователь раньше выбрал «буду коммитить»: вопроса нет;
- код 1 — внутри репозитория, `qa-runs/` не игнорируется: **один** вопрос «Добавить qa-runs/ в .gitignore этого репозитория?» — «Да (Recommended)» → `apply <OUTPUT_ROOT> --mode gitignore` (строка `/<путь от корня>/qa-runs/` в `.gitignore` корня репозитория) / «Нет, буду коммитить» → `apply <OUTPUT_ROOT> --mode keep` (ответ запоминается в `qa-runs/.gitignore-decision`, в следующих прогонах вопроса нет) / «Использовать .git/info/exclude (локально, без правки репозитория)» → `apply <OUTPUT_ROOT> --mode exclude`;
- код 2 — ошибка (нет git, нет папки): сообщить, ничего не править.

Без ответа ничего не правится. `apply` идемпотентен; код 1 после `apply` — строка записана, но её перекрывает правило с «!» (показать `git check-ignore -v`). Если файлы `qa-runs/` уже в индексе git (строка «уже в индексе git» в выводе, `tracked_files` в `--json`), `.gitignore` их не уберёт — показать команду `git rm -r --cached …` из вывода, но не выполнять её самому.
