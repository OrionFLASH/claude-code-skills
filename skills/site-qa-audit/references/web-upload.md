# Скриншоты через веб-форму GitHub (`screenshots: web-upload`)

Когда нужно: публикация в **чужой** (часто приватный) репозиторий, куда нельзя закоммитить картинки (`screenshots: commit` требует `push`), а REST API GitHub вложения не принимает. Единственный рабочий путь — загрузить файл через веб-редактор GitHub в браузере пользователя, где он **сам** вошёл, и вставить полученную ссылку `https://github.com/user-attachments/assets/…` в тело issue или комментарий.

Скрипты: `scripts/node/publish_web.mjs` (новый issue), `scripts/node/comment_web.mjs` (комментарий, в том числе к закрытому issue для `FIXED-INSUFFICIENT` / `REGRESSION`). Общая логика — `scripts/node/web_upload_lib.mjs`.

## Предпосылки
1. Chrome пользователя запущен с портом отладки, например `--remote-debugging-port=9222` (отдельный профиль: `--user-data-dir=<папка>`), и в этом окне **пользователь вручную вошёл на GitHub**. Скрипт подключается по CDP (`--cdp http://127.0.0.1:9222`).
2. `gh` авторизован (`gh auth status`) — он создаёт issue, правит тело и читает результат. Токены скрипт не видит и не печатает.
3. Права: создавать issues и комментировать в целевом репозитории; править тело **своего** issue.
4. Скриншоты проверены на персональные данные (`safety-rules.md` §5) — после загрузки ссылка доступна всем, у кого есть доступ к репозиторию.

## Как работает

### Новый issue — `publish_web.mjs`
1. Проверка входа: открыть `{base}/{repo}/issues`, прочитать `<meta name="user-login">`. Пусто или страница входа → **остановка**, код 4, сообщение «Нужен вход на GitHub в окне аудита…». Ничего не создаётся.
2. `gh issue create --body-file`: в теле на месте каждой картинки плейсхолдер `{{qa-shot:<имя файла>}}`. Локальные ссылки вида `![…](../screenshots/F-001-….png)` заменяются плейсхолдерами автоматически; для скриншота без ссылки плейсхолдер добавляется перед маркером `<!-- site-qa-audit:… -->`.
3. Открыть страницу нового issue и загрузить файлы через поле комментария (оно служит «площадкой загрузки»): кнопка «Paste, drop, or click to add files» → выбор файла; запасной путь — `input[type=file]` рядом с полем. Дождаться ссылки на вложение (текст «Uploading …» исчез). **Комментарий не отправляется**, поле очищается.
4. `gh issue edit --body-file`: плейсхолдеры заменяются фрагментами GitHub (`<img … src="…/user-attachments/assets/…">`).
5. `gh api repos/<repo>/issues/<N>`: в теле не меньше вложений, чем файлов; нет плейсхолдеров и «Uploading». Иначе код 5.

На странице issue не нажимается ни одна кнопка, кроме кнопки прикрепления файла.

### Комментарий — `comment_web.mjs`
1. `gh api`: запомнить состояние issue (`open` / `closed`).
2. Открыть issue в браузере, проверить вход (как выше).
3. Загрузить файлы в поле комментария, вставить итоговый текст (плейсхолдеры заменены, в конце скрытая отметка `<!-- site-qa-audit:web=<nonce> -->` для поиска по API). Если в тексте остался плейсхолдер — остановка **до** нажатия.
4. Нажать **только** кнопку с текстом ровно «Comment». Кандидаты фильтруются по видимому тексту, `aria-label` и `title`; всё, где есть Close / Reopen / Delete / закрыть / переоткрыть, пропускается; перед нажатием текст проверяется ещё раз. Нет чистого кандидата — остановка, код 6.
5. `gh api`: комментарий с отметкой есть, в нём вложения и нет плейсхолдеров; **состояние issue не изменилось** (закрытый остался закрытым). Иначе код 5.

## Устойчивые селекторы (новый интерфейс GitHub)
Новый интерфейс не использует `<form>` и `textarea[name="comment[body]"]`. Поиск поля — по порядку, берётся последнее видимое (поле нового комментария — внизу страницы):
1. placeholder «Use Markdown to format your comment»;
2. textbox с доступным именем «Markdown value»;
3. `textarea[aria-label*="comment" i]`;
4. `textarea[name="comment[body]"]` — старый интерфейс.

Если ничего не найдено — ошибка с перечнем всех попыток. Кнопки ищутся по тексту на странице, а не внутри формы.

## Запуск
```bash
# план (по умолчанию dry-run: ничего не создаёт, печатает шаги и итоговое тело)
node <SKILL_DIR>/scripts/node/publish_web.mjs --repo owner/repo --title "<заголовок>" \
  --body-file <RUN_DIR>/drafts/owner__repo/01-NEW-<fp>.md \
  --shot <RUN_DIR>/screenshots/F-001-menu-annotated.png --label bug

# реальная публикация — только после подтверждения пользователя
node <SKILL_DIR>/scripts/node/publish_web.mjs ...те же аргументы... \
  --cdp http://127.0.0.1:9222 --blocked-log <RUN_DIR>/logs/blocked.jsonl \
  --out <RUN_DIR>/logs/publish-F-001.json --confirm-publish

# комментарий к закрытому issue
node <SKILL_DIR>/scripts/node/comment_web.mjs --repo owner/repo --number 42 \
  --body-file <RUN_DIR>/drafts/owner__repo/42-comment.md --shot <RUN_DIR>/screenshots/F-007-annotated.png \
  --cdp http://127.0.0.1:9222 --confirm-publish

# только проверка по API (например, после сбоя)
node <SKILL_DIR>/scripts/node/publish_web.mjs --verify-only --repo owner/repo --number 42 --expect 1
```
Результат (JSON в stdout и `--out`): `repo`, `number`, `url`, `kind`, `attachments`, `ok`, `problems`. Записать в `findings.json` → `published` (`repo-sync.md` §4 п. 11).

Коды выхода: 0 — готово; 1 — неверные аргументы; 2 — окружение (нет CDP, ошибка `gh`); 3 — переход вне `--base-url`; 4 — нет входа / нет поля комментария; 5 — проверка по API не пройдена; 6 — защитная остановка (нет кнопки ровно «Comment» или кнопка выглядит опасной); 7 — загрузка не завершилась.

## Безопасность
- Реальное действие — **только** с `--confirm-publish`, который ставится после «да» пользователя на сводную таблицу публикации (`repo-sync.md` §4). Это и есть разрешение B4 на отправку комментария.
- Скрипт не входит в GitHub, не вводит логины, пароли и токены, не читает cookies и хранилище браузера.
- Замок хоста: навигация документа только на хост `--base-url`; попытки уйти — в `blocked.jsonl`. Нативные диалоги отклоняются.
- Close / Reopen / Delete не нажимаются никогда (явный запрет в коде и повторная проверка текста). Изменение состояния issue после комментария — ошибка проверки.
- Вкладки скрипт открывает сам и сам закрывает; окно и сессия пользователя не трогаются.
- Правила сайта (`rules.json`, `guard.js`) к браузеру GitHub не применяются: у них свой `allowed_domains`, и комментарий для них — `send-to-people`. Вместо этого — замок хоста и явное согласие `--confirm-publish`.
- Пауза между действиями — `--throttle` (по умолчанию 1500 мс); лимиты API — `repo-sync.md` §4 п. 10.

## Ограничения
- Вложение в приватном репозитории видно только тем, у кого есть к нему доступ.
- При загрузке через поле комментария на странице нового issue GitHub хранит файл как вложение репозитория даже без отправки комментария — это нормально, ссылка постоянная.
- Если загрузка оборвалась после создания issue, issue остаётся с плейсхолдером (скрипт сообщает номер): повторить загрузку или поправить тело вручную, затем `--verify-only`.
- Интерфейс GitHub меняется: при ошибке «Поле комментария не найдено» скрипт перечисляет попытки — сообщить пользователю и не подбирать селекторы наугад на чужом репозитории.
- Проверено только на локальных фикстурах (`tests/test_stream_c.sh`), не на github.com.
