# E07. Дельта между прогонами: точность сопоставления и экономия времени
Предложение: P004 «Дельта между прогонами: новые, исправленные и вернувшиеся находки» · Ставка: 3 · Тип: ручной сервис (консьерж) + офлайн-проверка точности; до/после по времени

Обоснование не повторяется: `data/proposals.json` → P004; ставка 3 — `build/strategy-facts.md`, раздел «Три главные ставки».

## Гипотеза
Если к отчёту повторного прогона добавить блок «Новые / Исправлено / Вернулось / Без изменений» по fingerprint, то время ответа на вопрос «что изменилось с прошлого раза» сократится с ≈ 10 минут до ≤ 1/3 исходного [допущение: P004, `effect_kpi` «10 мин → 1 мин»] при точности классификации находок ≥ 90 %, потому что отпечаток находки уже считается, а сравнения двух прогонов цели нет (`skills/site-qa-audit/scripts/fingerprint.py:202-213`; P004, текущее состояние).

## Метрики
- **Основная, стадия 1:** доля верно классифицированных находок (новая / без изменений / вернулась / исправлена) относительно ручной разметки владельца. Бинарная на находку.
- **Основная, стадия 2:** медианное время ответа «что появилось, что исправлено, что вернулось» без дельты и с дельтой.
- **Вспомогательные:** доля неуверенных совпадений («возможно то же», P004 риски); ошибки по типам: ложное «исправлено» и ложное «новая»; верность ответов в стадии 2.
- **Защитные (с порогом):** (а) ложное «исправлено» ≤ 5 % находок [допущение] — самая вредная ошибка, она прячет живой баг; превышение → дельта не выпускается без статуса «возможно то же»; (б) ручная сборка дельты ≤ 30 минут на пару прогонов [допущение] — иначе консьерж-проверка сама искажает оценку времени.

## Дизайн
- **Почему не A/B.** Повторных прогонов у внешних пользователей нет (расчёт ниже).
- **Стадия 1 (офлайн, точность):** 2–4 пары реальных `findings.json` одной цели из прошлых прогонов владельца [допущение: такие пары есть], ≥ 40 находок суммарно; набор фиксируется до сопоставления. Владелец размечает вручную «та же / другая» вслепую, затем сопоставление по fingerprint — существующими подкомандами `fingerprint.py` (`compute`, `match` с порогом по умолчанию 0,35 — `fingerprint.py:211`) или вручную по отпечаткам; сравнить с разметкой.
- **Стадия 2 (консьерж, до/после по времени):** 4 участника (владелец + 3 коллеги [допущение]); у каждого 2 пары отчётов X и Y: одна — без дельты (два отчёта рядом), другая — с ручным блоком дельты и строкой «новых +N, исправлено −M». Какая пара получает дельту — по жребию (перекрёстный дизайн, чтобы сложность пар не смешалась с эффектом).
- **Где в продукте:** `build_report` пока не меняется; дельта собирается вручную отдельным файлом.

## Размер выборки и длительность
**Почему A/B на пользователях невозможен.** Метрика «повторный прогон в течение 30 дней», p1 = 0,60 [допущение: `data/model.json`, base, `retention_monthly`], MDE +0,10 → p2 = 0,70; α = 0,05 (z = 1,96), мощность 80 % (z = 0,84):

n = (1,96 + 0,84)² × (0,60 × 0,40 + 0,70 × 0,30) / 0,10² = 7,84 × 0,45 / 0,01 ≈ **353 на группу**.

Активных внешних пользователей 0 [факт: `build/strategy-facts.md`, «Что уже есть»]; в базовом сценарии 4 активных в первый месяц ≈ 0,13 в день [допущение: `data/model.json`, base, `monthly[0].users`] → 2 × 353 / 0,13 ≈ 5 300 дней. Вывод: проверяем точность и экономию времени без пользователей.

**Стадия 1 (точный биномиальный критерий).** H0: точность ≤ 0,75 [допущение: наивное сопоставление], H1: 0,92; n = 40 находок; порог — **≥ 35 из 40 верных**.
- α_факт = P(X ≥ 35 | n = 40, p = 0,75) = 0,043.
- Мощность = P(X ≥ 35 | n = 40, p = 0,92) = 0,90.
- Пример: 36 из 40 → 90 %, 95 % интервал Уилсона 77–96 %.

**Стадия 2.** 4 участника × 2 пары = 8 замеров; статистический тест не планируется (выборка мала), решающий порог по величине эффекта: медиана с дельтой ≤ 1/3 медианы без дельты и 0 ошибок в ответах с дельтой [допущение].

**Длительность:** стадия 1 — 1–2 дня разметки; стадия 2 — 4 сессии в течение недели → **7 дней** (минимум).

## Критерий остановки
- Стадия 1: вывод после разметки всего зафиксированного набора (≥ 40 находок); замена пар после просмотра результатов запрещена.
- Стадия 2: вывод после 8 замеров; промежуточных решений нет.
- Защитная (а) оценивается на всём наборе стадии 1, досрочной остановки по ней нет.

## Решение по итогам
- **Победа** (≥ 35 из 40, ложное «исправлено» ≤ 5 %, порог стадии 2 выполнен): реализовать P004 в `build_report` с `history.json`; набор стадии 1 — регрессионный тест.
- **Ничья** (30–34 из 40 или эффект стадии 2 меньше порога): реализовать со статусом «возможно то же» для неуверенных совпадений; порог сопоставления подобрать на наборе стадии 1 и проверить на новой паре.
- **Проигрыш** (< 30 из 40 или ложное «исправлено» > 5 %): дельту на текущем fingerprint не строить; сначала стабилизировать отпечаток (шаблоны URL, элементы) отдельной задачей.

## Риски и этика
- `findings.json` могут содержать URL и скриншоты чужих сайтов: коллегам — только пары по собственным или учебным целям, без раскрытия клиентов.
- Ничего не публикуется. Платящих нет — влияние не применимо.

## Что нужно для запуска
- **События аналитики:** таблица разметки (id находки в прогонах 1 и 2, ручная метка, автоматическая метка, отпечаток); протокол стадии 2 (участник, пара, с дельтой или без, время, ошибки).
- **Флаги:** не нужны.
- **Тексты:** шаблон ручной дельты (4 раздела + строка «новых +N, исправлено −M»), вопрос стадии 2.
- **Дизайн:** макет не нужен.
- **Предусловия:** пары `findings.json` одной цели из прошлых прогонов.
